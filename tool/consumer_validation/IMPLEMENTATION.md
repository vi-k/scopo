# Реализация комплекта

Спецификация: задание владельца в текущей сессии. Дизайн утверждён; обсуждение,
подтверждения и git-операции исключены прямым указанием.

1. Зафиксировать внешний контракт и управляемый бэкенд; написать приёмку
   и увидеть её падение на пустом starter.
2. Реализовать два эталона разных семейств; проверить анализ и приёмку.
3. Внести независимые мутации; усилить приёмку при выживании.
4. Проверить аудит и API-отчёт, написать инструкции оценки и выполнить A–G.

Решение: ResourceChild из неизменяемого бэкенда делает последний доступ при
dispose, поэтому порядок проверяется наблюдаемым событием. Жизненный цикл
приложения остаётся ответственностью scopo.

- Собственные тесты: starter 3, data 4, controller 4; Python 9.

Независимое ревью нашло и помогло закрыть три дефекта комплекта: копирование
симлинков могло менять оригинал, пропуски тестов давали успешный exit code,
а быстрый повторный вход после Leave не проверял сериализацию. Для первых двух
добавлены сначала красные Python-регрессии, затем исправлен раннер; для
третьего — два сценария и отдельный убитый мутант.

Отклонение: первые Python-фикстуры использовали системный /tmp. Затем все
фикстуры перенесены под kit/.review-tmp, итоговый прогон использует только его.
Отказов песочницы не было. Бэкенд всех трёх приложений идентичен.

Регламент scopo-src не применялся к его изменению: клон не редактировался, его
handoff не обновлялся, коммиты и полный релизный гейт не выполнялись по прямым
ограничениям задания. Комплект находится в уже изолированном репозитории; новые
worktree и ветки не создавались.

## Протокол подготовленного прогона

Приёмка сохраняет `result.json` с отдельными списками успешных, проваленных,
пропущенных и незавершённых сценариев и сбоев инфраструктуры. Классификатор
мутаций читает этот файл по строке `Result:`; обрыв событий или пропуск
сценария даёт `INVALID`. Для `KILLED` нужен завершённый провал сценария при
корректном завершении всего прогона. Текстовые `PASS`/`FAIL` и последняя строка
Flutter сохраняются для читателя.

`prepare.sh` записывает коммит публичной копии и SHA-256 подготовленных файлов
`vendor/scopo/` и `kit/` в `manifest.json` корня прогона. Проверка G сравнивает
обе папки с этим снимком и называет лишние, пропавшие и изменённые файлы. Кеши
`.dart_tool`, `build`, `.review-tmp`, `__pycache__`, `.git` и `.fvm` исключены;
`.fvmrc` и подготовленные `pubspec.lock` проверяются. Режим E запускается
только с явным `--rollout`; иначе выдаёт `SKIP` с причиной. Отдельный
`scopo-src` и git-репозиторий в `kit/` для G не требуются.
