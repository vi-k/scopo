# Комплект проверки публичной документации scopo

Чтобы оценить решение, передайте исполнителю отдельную копию starter/
и task.md, а скрытую часть оставьте у владельца. Для полноценного эксперимента
рабочий каталог исполнителя должен находиться вне kit. Исполнитель этим
комплектом не запускается.

| Путь | Назначение |
| --- | --- |
| prepare.sh | Сборка прогона в отдельном каталоге: публичная копия, справочники, комплект, приложение исполнителя, бриф |
| brief/ | Начало и конец брифа исполнителя; между ними prepare.sh ставит task.md |
| task.md | Самодостаточное английское задание без имён API scopo |
| starter/ | Пустое приложение, неизменяемый управляемый бэкенд, тесты бэкенда |
| acceptance/ | 15 скрытых виджет-тестов a–e, включая общие проверки утечек и ошибок и три прогона дольше трёхсекундных лимитов пакета |
| reference/data/ | Эталон на AsyncDataScope |
| reference/controller/ | Независимый эталон на AsyncControllerScope и ScopeController |
| mutants/ | 10 независимых патчей к первому эталону и описание поломок |
| run_acceptance.sh | Приёмка во временной копии переданного приложения |
| run_mutants.sh | Проверка эталона, затем всех мутаций |
| audit_reads.py | Статический аудит команд и кандидатов прочитанных путей в rollout JSONL |
| api_coverage.py | Публичные имена из dartdoc index и их присутствие в прозе |
| tool_tests/ | Регрессионные проверки Python-инструментов |
| rubric.md | Правила оценки агента и человека, классификация заминок |
| tools/verify.py | Автоматический прогон A–G с сохранением команд и полных логов |
| IMPLEMENTATION.md | Краткая внутренняя запись выполнения |

## Запуск

В репозитории scopo комплект хранится с подстановками вместо абсолютных
путей и сам не запускается. Работают с его копией, которую собирает
`sh tool/consumer_validation/prepare.sh <каталог прогона>` из HEAD
репозитория; ниже «корень kit» — это `<каталог прогона>/kit`. Порядок прогона
целиком — в `docs/consumer-validation.md` репозитория.

Из корня kit задайте export TMPDIR="$PWD/.review-tmp" и выполните mkdir -p
"$TMPDIR". Скрипты раннеров задают этот путь сами; mktemp без явного шаблона
не используйте. Все приложения содержат .fvmrc для Flutter 3.27.0 и симлинк SDK;
их создаёт prepare.sh, потому что git их не хранит. Зависимость scopo указывает
на неизменяемую публичную копию ../vendor/scopo абсолютным путём.

Для проверки результата выполните ./run_acceptance.sh /путь/к/приложению, затем
в оригинальном приложении fvm flutter analyze и fvm flutter test. Подробный
порядок, проверка бэкенда и условия провала находятся в rubric.md.

Приёмка копирует приложение в .review-tmp/acceptance-*/app, исключая кеши
и git. Симлинки приложения копируются как содержимое; .fvm создаётся заново.
В копию добавляется test/acceptance/, затем выполняются fvm flutter pub get
--offline и fvm flutter test с развёрнутым и JSON-отчётами. Имя пакета
в импортах тестов подставляется из pubspec.yaml. Вывод содержит PASS/FAIL
по каждому тесту и последнюю строку реального текстового раннера без префикса
времени и счётчиков. Полный оригинальный вывод сохранён в runner.log; события —
events.jsonl, разрешение зависимостей — pub-get.log. Неудача компиляции или
разрешения зависимостей возвращает ненулевой код. Строка `Result:` указывает
на `result.json`: завершённые успешные (`passed`), проваленные (`failed`),
пропущенные (`skipped`), незавершённые (`incomplete`) сценарии и сбои
инфраструктуры (`infrastructure_errors`). Классификатор читает этот итог;
`KILLED` возможен только при корректном завершении всего прогона и наличии
завершённого провала сценария. Обрыв событий, пропуск и ошибка инфраструктуры
дают `INVALID`, даже если другой сценарий успел завершиться провалом.

Полный воспроизводимый прогон подготовленного комплекта:
`python3 tools/verify.py --output ../verification`. Скрипт сохраняет
`verification.json` и отдельный лог каждой команды. Проверка G сверяет
`vendor/scopo/` и `kit/` с `manifest.json` в корне прогона: коммит scopo
и SHA-256 файлов после подстановок и подготовки зависимостей. Лишний, пропавший
или изменённый файл даёт `FAIL` с его именем. Каталоги кешей `.dart_tool`,
`build`, `.review-tmp`, `__pycache__`, `.git` и `.fvm` не входят в снимок;
`.fvmrc` и подготовленные `pubspec.lock` входят.

Режим E включается только явным `--rollout /путь/к/журналу.jsonl`; без него
печатается `SKIP` с причиной. Это аудит собственного журнала автора комплекта:
он ожидает найденное чтение `scopo-src`, а не чистый аудит исполнителя.

Для самопроверки комплекта запустите ./run_acceptance.sh reference/data,
./run_acceptance.sh reference/controller и ./run_mutants.sh. Последний сначала
проверяет зелёный базовый эталон; каждый мутант обязан дать KILLED. SURVIVED
означает дыру в приёмке, INVALID — ошибку инфраструктуры или компиляции,
которая убийством не считается. На starter/ приёмка обязана быть красной.
В каждом из трёх приложений отдельно выполните fvm flutter pub get --offline,
fvm flutter analyze и fvm flutter test. Python-проверки запускаются командой
python3 -m unittest discover -s tool_tests -v.

Для аудита выполните python3 audit_reads.py /путь/к/rollout.jsonl, передав
также журналы дочерних агентов этой попытки. Сессии codex exec находятся
в ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl. Выберите id нужной попытки;
самый свежий файл после параллельной работы может принадлежать другому агенту.
Код 0 означает отсутствие отмеченных кандидатов, 1 — наличие, 2 — неполный
разбор. Прочитайте ограничения статического анализа в конце отчёта: нулевой
счётчик не является доказательством отсутствия запрещённых чтений.

Для отчёта API выполните python3 api_coverage.py reference/data и python3
api_coverage.py reference/controller (либо передайте результат исполнителя).
Индекс берётся из ../vendor/api/index.json; проза — README.md и doc/*.md
публичной копии, без блоков кода. API-only разрешён заданием. Лексические
совпадения коротких имён проверяются человеком.

## Часы и границы проверки

Бэкенд создаёт задержки и управляющие futures в Zone.root. Приёмка чередует
короткие реальные ожидания внутри tester.runAsync и tester.pump. Это важно для
асинхронного разбора scopo: продвижение только fake clock не заканчивает
реальную работу. Управляемые ворота позволяют проверять запрещённое раннее
открытие и ранний уход независимо от скорости машины; ожидания успеха имеют
ограниченный запас реального времени.

Тесты ходят только через buildApp, ключи и бэкенд. Они не импортируют scopo
и не требуют конкретного семейства. Использование scopo проверяется отдельно
чтением результата; динамическая приёмка не доказывает архитектуру решения.
Оба эталона закрывают экран `close()` своего скоупа: ветка закрытия сразу
заменяет поддерево, future завершается после освобождения, и только тогда
экран уходит домой.
