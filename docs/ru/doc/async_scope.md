# AsyncScope

> Перевод `doc/async_scope.md` (blob `52f01666a9e242cb6dbf5107479baf1b71b1e74f`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Скоуп, всё содержимое которого — жизненный цикл: асинхронная инициализация и
асинхронная утилизация, без контейнера зависимостей и без класса состояния.
Берите его, когда объекты уже существуют — синглтон, соединение, репозиторий
родительского скоупа — и по дереву виджетов должны следовать только их запуск и
остановка.

```dart
AsyncScope(
  initScope: (context, ctx) async {
    ctx.progress('connecting');
    await connection.open();
  },
  disposeScope: () => connection.close(),
  waitingBuilder: (context) => const SizedBox.shrink(),
  progressBuilder: (context, progress) => Text('$progress'),
  errorBuilder: (context, error, stackTrace, progress) => Text('$error'),
  builder: (context) => const HomeScreen(),
);
```

`AsyncScopeBase` — форма для наследования: те же члены переопределениями —
`initScope`, `disposeScope`, `onMount`, `onUnmount`, `buildOnWaiting`,
`buildOnProgress`, `buildOnReady`, `buildOnError` — плюс `scopeKey`,
`scopeKeyTimeout`, `initCancellationTimeout`, `disposeScopeTimeout`,
`waitForChildrenTimeout`, их колбэки `onTimeout` и `pauseAfterInitialization`.
Под обоими лежит `AsyncScopeCore` — для скоупа, которому нужен свой элемент.

## Четыре состояния

`AsyncScopeState` — запечатанная иерархия, и каждое состояние ведёт свой билдер:

| состояние | билдер | когда |
| --- | --- | --- |
| `AsyncScopeWaiting` | `buildOnWaiting`, а если он вернул `null` — `buildOnProgress` | встал на дерево; ждёт `scopeKey` и первое событие |
| `AsyncScopeProgress` | `buildOnProgress` | `initScope` сообщил о прогрессе; значение в `progress` |
| `AsyncScopeReady` | `buildOnReady` | `initScope` вернул управление |
| `AsyncScopeError` | `buildOnError` | `initScope` упал раньше, чем стал готов; вместе с ошибкой приходит достигнутый прогресс |

`initScope` говорит только две из этих четырёх вещей и не называет ни одну:
`ctx.progress(x)` — это прогресс, а возврат из тела — готовность. «Жду» и
«упал» принадлежат скоупу, а не работе: с первого скоуп начинает, второе из
него делает бросок.

Готовое состояние применяется не в том же кадре, в котором пришло событие. Без
`pauseAfterInitialization` скоуп планирует post-frame-колбэк, чтобы последнему
значению прогресса достался отдельный кадр, а не подмена внутри того кадра, в
котором он появился; с ним готовая ветка придерживается на заданное время.
`ScopeConfig.pauseAfterInitializationEnabled = false` выключает все такие паузы
глобально — см. тему `debug`.

## Прогресс

Прогресс — это то, чем его назовёт инициализация. `AsyncScopeProgress` несёт
`Object?`, билдеры получают `Object?`, и пакет внутрь не заглядывает. Обычный
случай — `String`; сгодится что угодно с `toString`.

```dart
AsyncScope(
  initScope: (context, ctx) async {
    ctx.progress('connecting');
    await api.connect();

    ctx.progress('loading the profile');
    await api.loadProfile();
  },
  disposeScope: api.close,
  progressBuilder: (context, progress) => Center(child: Text('$progress')),
  errorBuilder: (context, error, stackTrace, progress) =>
      Center(child: Text('failed at $progress: $error')),
  builder: (context) => const HomeScreen(),
);
```

Про аргумент `progress` стоит знать четыре вещи.

**До первого события он `null`.** Скоуп находится в `AsyncScopeWaiting` с
момента постановки на дерево и до первого сообщения, а если `buildOnWaiting`
вернул `null`, ветка ожидания — это `buildOnProgress(context, null)`. Пишите
билдер так, чтобы `null` значил «ещё ничего не сообщали»; то же он значит и в
`buildOnError`, когда провал случился раньше любого прогресса.

**Последнему значению достаётся свой кадр.** `AsyncScopeReady` применяется в
post-frame-колбэке, поэтому значение прогресса, сообщённое прямо перед
возвратом из тела, успевает отрисоваться, а не подменяется внутри того же
кадра.
`pauseAfterInitialization` придерживает готовую ветку ещё дольше — за ним и
тянутся, когда шаги слишком быстры, чтобы их прочитать.

**Прогрессу после готовности некуда идти.** Скоуп инициализируется один раз;
вызов прогресса после готовности — например, из оставленного работать
хелпера — игнорируется и на экран не влияет. Инициализации, которая
продолжает выдавать значения после того, как скоуп стал пригоден, нужен
`Listenable` под скоупом, а не этот контекст.

**Не сообщать прогресс вовсе — нормально.** `initScope`, который ничего не
сообщает, не выходит из `AsyncScopeWaiting`, так что скоуп показывает
`buildOnWaiting` — обычно спиннер, — а затем готовую ветку.

### Счёт шагов

Для инициализации, которая знает число своих шагов, есть `ProgressIterator`, а
`Progress` — значение, которое он выдаёт: `number`, `total`, `value` как доля
от 0 до 1 и `toString` вида `2/3`.

```dart
initScope: (context, ctx) async {
  final steps = ProgressIterator(3);

  ctx.progress(steps.nextStep()); // 1/3
  await api.connect();

  ctx.progress(steps.nextStep()); // 2/3
  await api.loadProfile();

  ctx.progress(steps.nextStep()); // 3/3
  await api.warmUpCache();
},
progressBuilder: (context, progress) => switch (progress) {
  final Progress progress => LinearProgressIndicator(value: progress.value),
  _ => const LinearProgressIndicator(),
},
```

Доля всегда лежит между 0 и 1 — пустая работа читается как завершённая, а не как
`NaN`, — поэтому её можно отдавать индикатору как есть. См. тему `utils`.

### Где тип возвращается

`ctx.progress` принимает `Object`, билдеры получают `Object?`, так что тип
значения прогресса объявляет билдер: `buildOnProgress` может сказать
`covariant Progress? progress` и читать поля, а не звать `toString`.
`ScopeAutoDependencies` сообщает `ScopeAutoDependenciesProgress` на каждую
зависимость — путь, имя и счётчик шагов в одном объекте. См. тему `Scope`.

Внутрь значения прогресса пакет не заглядывает никогда. Прогресс — это
подпись; параметр типа, который у семейства есть, принадлежит строящемуся
значению.

## Чтение состояния из поддерева

```dart
final scope = AsyncScope.of(context, listen: true);
if (scope.isInitialized) { … }
```

`of`, `maybeOf` и `select` возвращают `AsyncScopeContext`, который открывает
`state`, `isInitialized` (состояние — `AsyncScopeReady`), `hasError` и
`error` / `stackTrace`; последние два бросают `StateError`, когда ошибки нет.
Обычный вход — прочитать одно поле через `select`: он подписывает только на
него, а фильтрацию объясняет тема `base`.

## Ошибки

Тело, бросившее до готовности, переводит скоуп в `AsyncScopeError`, и
`buildOnError` получает ошибку, стек вызовов и прогресс, которого скоуп успел
достичь.

Один провал обрабатывается иначе, и о нём стоит знать.

**Ошибка без собственного исхода** — поздний отказ брошенного через `wait`
действия, ошибка диспозера или колбэка `onCancel`, сбой работы `unattended` —
доходит до `ScopeObserver.onError` и `FlutterError.reportError`.
Она не переключает экран на `buildOnError`, а готовый скоуп остаётся готовым.
Это сознательно: на экране виджеты готовой ветки, всё, что
захватил `initScope`, всё равно должен освободить `disposeScope`, а подмена
поддерева экраном ошибки за спиной у пользователя бросила бы и то и другое.
Тело, продолжающее работу после возврата — оставленный им хелпер, — случай
нечастый, но именно в нём разница и важна.
Ошибки асинхронной работы, запущенной в обход контекста, по-прежнему попадают
в её зону.

## Утилизация, по порядку

Разбор идёт одной последовательностью, и каждого асинхронного шага дожидаются:

1. **`onUnmount`** — синхронно и всегда первым. Здесь сбрасывают всё, что
   должно немедленно перестать доставать до скоупа: подписки, слушателей.
   Выполняется ровно один раз, каким бы способом скоуп ни уходил — снят с
   дерева или закрыт через `close()`, оставаясь на экране.
2. **Отменяется ожидание `scopeKey`**, если скоуп ещё стоял в очереди.
3. **Отменяется инициализация**, и ожидание отмены ограничено
   `initCancellationTimeout` (по умолчанию
   `ScopeConfig.defaultInitCancellationTimeout`). Отмена дожидается тела,
   его дочерних задач и уборки. Тело узнаёт о ней через `ctx.progress`,
   `check` или методы семейства ожиданий: они бросают `Cancelled` по своим
   правилам, описанным ниже. Ошибку, возникшую при раскручивании тела,
   репортят, а не бросают дальше:
   бросить разбор в этой точке значило бы оставить скоуп зарегистрированным у
   родителя, а `scopeKey` — неосвобождённым. Отмена, которая не завершается
   вовсе, оставит их там же, и ошибки для этого не требуется: тело,
   припаркованное на чужом future, не прерывает ничто, а телу, которое ничего
   не спрашивает у `ctx`, ничего и не говорят. По истечении лимита
   инициализацию оставляют как есть, истечение репортят, и разбор идёт дальше.
   То, что держит тело, так и остаётся у него, — а если оно закончит позже,
   произведённое им отдадут в `disposeScope`, если только разбор к тому времени
   не дошёл до конца. Уборка, зарегистрированная у задачи, не нуждается в
   этом хуке и всё равно выполняется.
4. **Инициализацию дожидаются**, если отменить её не удалось.
5. **Дожидаются дочерних скоупов**, с ограничением `waitForChildrenTimeout` (по
   умолчанию `ScopeConfig.defaultWaitForChildrenTimeout`). Истечение репортят
   через `FlutterError.reportError`, и разбор идёт дальше.
6. **`disposeScope`** — собственный разбор скоупа; если он вернул future, его
   дожидаются с ограничением `disposeScopeTimeout` (по умолчанию
   `ScopeConfig.defaultDisposeScopeTimeout`). Шаг выполняется, только если
   инициализация удалась: скоупу, который так и не стал готовым — всё ещё ждал
   или упал, — освобождать нечего. Разбор, который никогда не завершится, — это
   пользовательский код, держащий шаг 7 ниже, а с ним и `scopeKey` скоупа,
   которого уже нет на дереве; по истечении лимита это репортят, шаг 7
   выполняется всё равно, а сам разбор дорабатывает когда доработает.
7. **Скоуп снимается с учёта у родителя и освобождает `scopeKey`**, пропуская
   следующий скоуп, ждущий этот ключ.

Каждый шаг защищён по отдельности: отказ в одном никогда не повод пропустить
те, что за ним. Передать наружу можно только один отказ — больше бросок не
несёт, — и это первый, отданный после того, как вся последовательность
кончилась: тому, кто позвал `close()`, а для скоупа, снятого с дерева, — зоне, в
которой шёл разбор. Каждый отказ за ним вместо этого репортится через
`FlutterError.reportError`.

Ради этого порядка семейство и берут: родитель никогда не утилизирует то, чем
ещё пользуется ребёнок, а пересозданный скоуп никогда не пересекается с тем,
которого он сменяет.

### Упавшая инициализация убирает за собой сама

Шаг 6 стоит прочитать дважды: **`disposeScope` выполняется, только если
инициализация удалась.** Скоуп, упавший на полпути, до него не доходит, и
второго хука, который дошёл бы, нет: `onUnmount` отрабатывает, но ему нечего
передать.

Это не недосмотр и не долг, который когда-нибудь закроют: **упавшему скоупу
нужна частичная утилизация, и какая именно её часть — знает только тот код,
который его строил.** `disposeScope` пишут для законченного скоупа, и он делает
полную; заставить его ещё и выяснять, докуда дошла инициализация, значит внести
этот вопрос ровно в тот хук, который от него свободен. Значит, отдавать взятое
до провала — дело самой инициализации:

```dart
// Неправильно: соединение открыто, и закрыть его теперь некому.
initScope: (context, ctx) async {
  connection = await Api.connect();
  await connection.authenticate();           // бросает
},
disposeScope: () => connection.close(),      // не будет вызван
```

```dart
// Правильно: что шаг взял, то и отдаётся, если скоуп это не забрал себе.
initScope: (context, ctx) async {
  final opened = await Api.connect();

  try {
    ctx.progress('authenticating');
    await opened.authenticate();
  } on Object {
    await opened.close();
    rethrow;
  }

  connection = opened;
},
disposeScope: () => connection.close(),
```

**`catch`, и никакого флага** — обе половины стоит проговорить, потому что
прежней форме этого пакета требовалось ровно обратное и тому и другому.

Инициализация кончается досрочно двумя способами: падает её шаг — или скоуп
уходит, так и не став готовым: его убрали из дерева или закрыли через
`close()`. В обоих случаях в тело бросается исключение — при отмене это
`Cancelled`, брошенный в точке проверки вроде `ctx.progress` между двумя
шагами, — поэтому один `catch` покрывает и то и другое. `Cancelled` приходит из
`async_job` и реэкспортирован из `scopo`: для его перехвата не нужна отдельная
зависимость или импорт.

Тело, не трогающее контекст нигде, — исключение, подтверждающее правило: ему не
бросают ничего, потому что Dart не прерывает чужое ожидание, и оно доработает
до конца для скоупа, которого уже нет. Это не дыра. Произведённое им тогда
отдадут в `disposeScope`, а не потеряют, — и следующий раздел ровно про это
обещание.

Флага нет, потому что защищаться не от чего. Возврат — это и есть передача, и у
тела, которое вернуло управление, строк больше не осталось: дойти до `catch` и
дойти до передачи — взаимоисключающие исходы по построению, так что защита не
может отдать то, что скоуп уже забрал. Там, где защите нужно знать разницу
*изнутри* — тело из нескольких шагов, отдающее их в обратном порядке, —
собирайте освобождения по мере того, как берёте:

```dart
final acquired = <Future<void> Function()>[];

try {
  final database = await Database.open();
  acquired.add(database.close);

  ctx.progress('connecting');
  final session = await Session.connect();
  acquired.add(session.close);

  connection = Connection(database, session);
} on Object {
  for (final release in acquired.reversed) {
    await release();
  }
  rethrow;
}
```

Следите, чтобы то, чего защита дожидается, умело заканчиваться. Ниже по потоку
отказ виден не раньше, чем с ним закончит тело, поэтому `await` внутри защиты
удерживает не только ресурс, но и сам отказ: `close()`, который никогда не
завершится, оставит скоуп на ветке загрузки до истечения
`initCancellationTimeout` — ничего на экране и ничего в консоли. Собственные
ожидания скоупа ограничены именно поэтому, и то, которое за вас делает
контейнер зависимостей семейства `Scope`, — тоже. Защита, которую вы пишете
сами, и уборка, зарегистрированная у задачи, тоже должны уметь заканчиваться:
задача не ставит лимит на диспозер.

### Что идёт через контекст, а что нет

`ScopeInitContext` добавляет `progress` к `JobContext`. Dart не прерывает
чужое ожидание, поэтому тело узнаёт об отмене в точках проверки: `progress`,
`check`, `wait`, `join`, `uncancellable`, `onCancel` и `run`. Регистрировать
уборку и запускать работу через `unattended` можно и после отмены, пока
задача не закончилась; `ctx.job.isCancelled` отвечает без броска.

**`wait` с `discard:` — та форма, которую и берут, когда приобретение можно
оставить доигрывать.** Он заканчивает ожидание, а не работу. Действие
доигрывает, но значение есть кому закрыть, даже если до тела оно не дойдёт:

```dart
final opened = await ctx.wait(Api.connect, discard: (api) => api.close());
```

Правило одно: **значение, не дошедшее до тела, убирают безусловно; дошедшее
кладут на стек уборки.** Брошенный `wait` кладёт значение на стек, пока задача
ещё его раскручивает, или закрывает на месте, если задача уже закончилась.
На стеке `discard:` выполняется при отказе или отмене, а `dispose:` — при
любом исходе. Для временного файла, блокировки или подписки, которую тело
оставляет себе, берите `dispose:` и передавайте только один из двух.

Для чтения, прогрева или паузы освобождать может быть нечего:

```dart
await ctx.wait(cache.warmUp);   // отпускаем, как только скоуп сдался
```

**`join` — для вызова, который нельзя бросить на полпути:** миграции, записи
в устройство, чужого `init`. Он сразу принимает отмену, но дожидается конца
вызова и только затем бросает `Cancelled`; если сам вызов бросит ошибку,
она передаётся как есть. Он заменяет прежнюю пару `await x(); ctx.check();`,
объединяя ожидание и проверку в одном вызове:

```dart
await ctx.join(database.migrate);
```

Если `join` возвращает ресурс, передайте `discard:` или `dispose:` и ему:
значение, которого тело не получит, освободят до броска отмены. `ctx.check()`
остаётся там, где нечего оборачивать, — например, в цикле собственной работы.
`await ctx.uncancellable(step)` придерживает отмену для шага, который нельзя
отменять вовсе; отмена доходит, когда шаг закончится. `ctx.unattended(work)`
запускает работу, которой никто не ждёт, и сообщает её ошибки наблюдателю;
он не дожидается этой работы и не отменяет её.

Для значения, которое тело уже держит, `onDispose` и `onDiscard` регистрируют
те же два вида уборки. Они возвращают функцию, снимающую регистрацию;
`disown(value)` снимает уборку, привязанную к значению через `wait` или `join`.
Стек раскручивается в обратном порядке регистрации, после завершения
дочерних задач и до того, как задача сообщит исход. Каждого освобождения
дожидаются:

```dart
ctx.onDispose(temporary.close);          // освобождается при любом исходе
final unregister = ctx.onDiscard(session.close); // при отказе или отмене
final opened = await ctx.wait(Api.connect, discard: (api) => api.close());

connection = Connection(opened, session);
// Передано скоупу: теперь оба ресурса освобождает его disposeScope.
ctx.disown(opened);
unregister();
```

Снимайте регистрации при передаче, без `await` или точки проверки между ней
и возвратом. Иначе уборка отменённой задачи и освобождение позднего возврата
скоупом закроют один ресурс дважды. У регистрации через `onDispose` или
`onDiscard` нет привязанного значения, поэтому `disown` её не снимет;
используйте возвращённую функцию, как выше.

**Голый вызов по-прежнему верен для короткой инициализации, которая ничего
не спрашивает у контекста.** Безопасно это не по надежде, а по обещанию
скоупа: **тело, вернувшееся к скоупу, который уже сдался, ничего не
устанавливает, но произведённое им освобождают, а не теряют** — здесь
`disposeScope`, в теме `AsyncDataScope` — `disposeData`, в теме `Scope` —
собственный разбор контейнера. Единственный путь, где это невозможно, — разбор,
который уже закончился, то есть истёкший `initCancellationTimeout`: к этому
моменту у скоупа не осталось виджета, из которого читается хук.

Если у зависимостей есть свой порядок, контейнер семейства `Scope` хранит
их дерево и ведёт разбор — см. тему `Scope`. `AsyncControllerScope`
закрывает ту же дыру с другой стороны: его
контроллер утилизируется на **любом** пути, включая тот, где `init()` бросил.

## Родители и дети

Каждый асинхронный скоуп встаёт на учёт у ближайшего `AsyncScopeParent`
сверху — у родительского скоупа, если он есть, иначе у
`AsyncScopeCoordinator`, — и именно этого дожидается шаг 5 выше. Миксин
открывает то, что знает:

```dart
hasChildren;    // bool
childrenCount;  // int
await waitForChildren(timeout: …, onTimeout: …);
```

Получателя нарочно нет: **миксин лежит на элементе**, а элементы всех пяти
встроенных семейств приватные. То есть эти трое — для собственного скоупа,
семейства, построенного на `AsyncScopeCore`, которое читает их на `this`, а не
для поддерева, которое смотрит вверх. `AsyncScope.of(context, listen: false)` и
его собратья отдают `AsyncScopeContext`, где лежит состояние скоупа и ничего из
этого.

Из поддерева ожидание, которое можно попросить, — координаторское:

```dart
await AsyncScopeCoordinator.waitForChildren(context);
```

Оно дожидается скоупов, вставших на учёт у ближайшего координатора, — тех, над
которыми нет родительского скоупа, — а не детей одного конкретного скоупа.
Дождаться именно их, снаружи того скоупа, которому они принадлежат, встроенные
семейства не предлагают.

`waitForChildren` дожидается детей, зарегистрированных **на момент вызова**.
Ребёнок, вставший на учёт во время уже идущего ожидания, этим ожиданием не
дожидается и остаётся зарегистрированным после него. При истечении детей,
которые так и не закончили, отбрасывают, зовут `onTimeout` — по умолчанию это
`FlutterError.reportError` с именем скоупа, и ваш собственный колбэк получает
ту же названную ошибку, — и future в любом случае завершается нормально. Дедлока здесь нет: всё вырождается в задержку и
сообщение.

Скоуп, над которым нет ни родительского скоупа, ни координатора, не встаёт на
учёт нигде, и его никто не дожидается. Это стоит знать до того, как убирать
координатор, который выглядел декоративным.

## scopeKey и координатор

`scopeKey` выстраивает в очередь скоупы, которые не должны пересекаться. Скоуп
с ключом ждёт в голове очереди, пока предыдущий владелец ключа не закончит
утилизацию — все семь шагов выше, а не только уход с дерева.

Очереди принадлежат ближайшему `AsyncScopeCoordinator`:

```dart
AsyncScopeCoordinator(child: MaterialApp(home: HomeScreen()))
```

Из слова «ближайший» следуют два вывода. Два скоупа с одинаковыми ключами под
разными координаторами никогда не ждут друг друга. И очереди живут на элементе
координатора, поэтому очерёдность держится ровно столько, сколько живёт этот
элемент: замена координатора — другой `ValueKey`, другое место в дереве —
выбрасывает его очереди вместе с ним. Поэтому его место выше всего, что может
быть заменено, а обычное такое место — над `MaterialApp`.

Скоуп с `scopeKey` и без координатора сверху падает громко:

```text
No AsyncScopeCoordinator.
The AsyncScopeCoordinator is missing in the context. Add it to the widget tree
so that all your scopes that need it can access it. The most universal solution
is to place it above MaterialApp. …
```

Координатор заодно является корнем ожидания для тех скоупов своего поддерева, у
которых нет родительского скоупа, — благодаря этому он полезен и вовсе без
`scopeKey`:

```dart
await AsyncScopeCoordinator.waitForChildren(context);
```

перед разбором теста или перед уходом с заставки. Его `timeout` по умолчанию —
`ScopeConfig.defaultWaitForChildrenTimeout`, а истечение ведёт себя ровно так
же: о нём сообщают, его не бросают.
