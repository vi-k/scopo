Наблюдатель и глобальные настройки пакета. Всё на этой странице статическое
и живёт в `ScopeConfig`, поэтому обычное место для настройки — `main()`,
до `runApp`.

## Наблюдатель

Пакет молчит, пока ему не дадут, куда говорить. `ScopeConfig.observer`
по умолчанию `null`; присвойте ему `ScopeObserver` — и каждый скоуп приложения
начнёт отчитываться через него.

```dart
void main() {
  ScopeConfig.observer = const ScopePrintObserver();

  runApp(const App());
}
```

`ScopeObserver` — класс из двенадцати методов, и все двенадцать пустые.
Наследник переопределяет то, что ему нужно, и наследует молчание остальных, так
что наблюдатель, которому интересны только отказы, состоит из одного метода:

```dart
final class CrashReporter extends ScopeObserver {
  const CrashReporter();

  @override
  void onError(
    ScopeObservable target,
    ScopePhase phase,
    ScopeErrorRoute route,
    Object error,
    StackTrace? stackTrace,
  ) {
    // Любой другой маршрут: отказ уже у кого-то ещё, или это не отказ.
    if (route != ScopeErrorRoute.observer) return;

    crashlytics.recordError(
      error,
      stackTrace,
      reason: '${target.debugLabel}: ${phase.name}',
    );
  }
}
```

Он передаёт дальше только то, о чём `route` говорит, что больше оно никуда
не уходит. Остальное есть у кого-то другого: у `FlutterError.onError` или
у зоны, где сбор падений приложения обычно уже слушает, либо у кода, вызвавшего
`close()`: ему отказ передан. Передать его ещё раз значило бы сообщить о нём
дважды. То, что говорит `cancellation`, вовсе не отказ. См. «`onError`
и `ScopeErrorRoute`» ниже.

`ScopeObserver` — обычный класс: наследнику модификатор класса не требуется,
а тестовый двойник может его реализовать. Обычного наблюдателя наследуйте
от него, чтобы новые пустые хуки доставались по наследству.

`ScopeConfig.observer` держит одного наблюдателя, а хотеть двоих — обычное
дело: того, что выше, рядом с `ScopePrintObserver`, пока идёт работа. Для этого
есть `ScopeCompositeObserver`:

```dart
ScopeConfig.observer = const ScopeCompositeObserver([
  ScopePrintObserver(),
  CrashReporter(),
]);
```

Он часть пакета, а не то, что пишут руками, и в этом весь смысл. Пустые хуки
выше — это то, что позволяет обычному наблюдателю продолжать компилироваться,
когда позже добавят новый; делегат — единственный наследник, которому от них
нет никакой пользы: новый хук достался бы ему пустой реализацией из базы, и все
наблюдатели за делегатом молча перестали бы слышать это событие. Этот написан
вместе с тем классом, который он передаёт дальше. Упавший наблюдатель здесь
тоже не останавливает тех, кто за ним: отказ отчитывается, а остальных
спрашивают.

Хуки зовутся синхронно — из той сборки, инициализации или разбора, которым они
принадлежат. Именно это делает их полезными: порядок строк — это порядок,
в котором пакет делал работу. По той же причине упавший хук ловится,
а не выпускается наружу; об этом — раздел «Когда падает сам наблюдатель».

## Двенадцать хуков

| хук | что произошло |
| ---------------------------- | ----------------------------------------- |
| `onInit(target)` | началась инициализация |
| `onStepStarted(target, path)` | начался один её шаг |
| `onProgress(target, progress)` | сделан один её шаг |
| `onReady(target)` | она успешно закончилась |
| `onCancelled(target)` | она отменена, не дойдя до конца |
| `onDispose(target)` | начался разбор |
| `onDisposalStepStarted(target, path)` | начался один его шаг |
| `onDisposalProgress(target, path)` | сделан один его шаг |
| `onDisposed(target)` | разбор закончился |
| `onError(target, phase, route, error, stackTrace)` | что-то упало |
| `onTimeout(target, what, error, stackTrace)` | истекло ограниченное ожидание |
| `onTrace(target, message)` | шаг механики под жизненным циклом |

Четыре из них — шаги контейнера зависимостей: `onStepStarted` и `onProgress`
на инициализацию, `onDisposalStepStarted` и `onDisposalProgress` на разбор, —
и складываются они в две пары: вход и выход на каждую половину его жизненного
цикла. Оба входа шлются изнутри шага и до того, как он чего-либо дождётся, —
этим пары и ценны, см. «Последний вход без выхода» ниже. `onProgress` —
единственный из четырёх, который шлёт и скоуп, от себя; остальные три приходят
только от контейнера.

### Кто их шлёт

Семейство без собственной фазы инициализации — `ScopeWidget`, `ScopeModel`,
`ScopeNotifier`, `AsyncScopeCoordinator` — шлёт `onInit`, когда его элемент
проинициализирован, и пару `onDispose`/`onDisposed` вокруг своего разбора. Это
всё, что такому скоупу есть сказать, когда он работает; тот, у кого упал
`init()`, шлёт `onError` с `ScopePhase.initialization` и больше ничего.
До появления этой отчётности он не говорил ничего: его жизненный цикл был виден
только отладчику.

Семейство, у которого есть своя инициализация, — всё, что построено
на асинхронном элементе: `AsyncScope`, `AsyncDataScope`,
`AsyncControllerScope`, `LiteScope` и `Scope`, — шлёт вместо неё эту фазу,
во всех подробностях, которые у фазы есть: `onInit`, затем `onProgress`
на каждый шаг, затем `onReady` или `onCancelled`; а на выходе — `onDispose`
и `onDisposed`. Обе половины не шлёт никто: у этих семейств структурная пара
подавлена, поэтому `LiteScope` даёт один `onInit`, а не два.

Три обстоятельства, которых этот порядок не называет, и все три важны
наблюдателю, который складывает события в пары:

- **`onCancelled` не всегда идёт следом за `onInit`.** Скоуп, который сняли
  с дерева, пока он ещё стоял в очереди за своим `scopeKey`, собственной
  инициализации не начинал — объявлять было нечего: вся его запись это
  `onCancelled`, `onDispose`, `onDisposed`. Отмена и правда происходит
  в очереди, до той инициализации, о которой это семейство иначе отчиталось бы;
- **`onDispose` и `onDisposed` всегда приходят парой.** `onDispose` шлёт любой
  разбор, в том числе разбор скоупа, который так и не стал готовым и своего
  освобождать не будет, а `onDisposed` шлётся и тогда, когда разбор упал, —
  после `onError`, который об этом сказал, а не вместо него. Так что счётчик
  утечек или трекер интервалов, который открывается на одном и закрывается
  на другом, остаётся сведённым, куда бы скоуп ни ушёл;
- **у семейства без собственной фазы та же пара требует того `onInit`,
  который бы её открыл.** `ScopeWidget`, `ScopeModel`, `ScopeNotifier`
  и `AsyncScopeCoordinator` шлют `onDispose`/`onDisposed` только для элемента,
  чей `init()` завершился успешно; тот, что упал или не запускался вовсе,
  не шлёт ни одной половины — открытым ничего не объявляли, значит и закрытым
  объявлять нечего, хотя внутри себя элемент всё равно разбирается. Здесь два
  вида семейств расходятся: семейства со своей фазой из предыдущего пункта всё
  ещё способны закрыть разбор, открывшийся вовсе без `onInit`. Сам отказ при
  этом не теряется ни у тех, ни у других: `init()` — единственный хук, который
  оба вида выполняют раньше всего остального, и его падение шлёт `onError`
  с `ScopePhase.initialization` в обоих случаях.

Контейнер автоматических зависимостей `Scope` отчитывается о собственном
жизненном цикле под своей меткой, рядом со скоупом, которому принадлежит:
`onInit`, затем `onStepStarted`/`onProgress` на каждую проинициализированную
зависимость, `onReady` или `onCancelled`, а дальше `onDispose`,
`onDisposalStepStarted`/`onDisposalProgress` на каждую освобождённую
зависимость и `onDisposed`.

Одна зависимость не шлёт ничего, кроме `onTrace`: две точки, где она
разбирается с собственной ошибкой. Четыре шаговых события выше — это её шаги,
но события контейнера: они приходят под меткой контейнера, а именно её и держит
наблюдатель, который фильтрует по объекту события.

### Последний вход без выхода

`onStepStarted` шлётся изнутри шага, до того как инициализатор чего-либо
дождётся, а `onProgress` про тот же шаг — когда шаг сделан. Поэтому запись
зависшей инициализации кончается путём того шага, в котором она зависла:

```text
scopo | AppDeps(#1a2b7) | initialize…
scopo | AppDeps(#1a2b7) | initialize storage/db…
scopo | AppDeps(#1a2b7) | progress: storage/db (1/3)
scopo | AppDeps(#1a2b7) | initialize network/session…
```

В `network/session` вошли и не вышли. Больше об этом в записи не говорит
ничего: `progress` считает законченное, а шаг, следующий за `storage/db`,
угадывается только для группы `sequential` — у `concurrent` шагов в полёте
сразу несколько, и номер последнего законченного не говорит, который из них
застрял.

`onDisposalStepStarted` и `onDisposalProgress` — та же пара для разбора,
и читается она так же.

Две вещи пары обещают, и одну не обещают:

- **путь у обеих половин — одна и та же строка.** Её собирают одни и те же
  группы одним и тем же кодом на подъёме, поэтому `path` годится в ключ
  словаря, который открывается на входе и закрывается на выходе;
- **освобождение объявляют только тогда, когда есть что освобождать.**
  Зависимость, не зарегистрировавшая ничего или один только `unmount`,
  асинхронного разбора не имеет, и голый вход по ней читался бы как зависшее
  освобождение. Её проходят молча, поэтому непарный вход всегда значит ровно
  то, на что похож;
- **зависимость вашего собственного изготовления входа не объявляет.** Той, что
  реализует `ScopeDependency` сама, а не построена через `dep`, `sequential`
  или `concurrent`, отметку взять неоткуда. Оба её выхода по-прежнему приходят:
  `onProgress` передаётся через колбэк `onStep` метода `init()` — той частью
  договора, которую такая зависимость и реализует, а её освобождение объявляют
  за неё — группа над ней, когда путь проходит через неё, или, если такая
  зависимость и есть всё дерево, колбэк самого контейнера. Последний случай —
  единственное место, где обещание ниже кончается: дерево, чей корень ваш и чей
  разбор ведёт кто-то другой, не объявляется вовсе, потому что контейнер
  не получает колбэка от этого обхода.

У входа три исхода, и событиями из них являются только два: выход, `onError`
фазы `ScopePhase.disposal` и молчание. Отказ приходит сразу за тем входом,
который он закончил, поэтому упавшее освобождение не спутать с зависшим,
а вход, за которым нет ничего, значит, что шаг ещё идёт — или не вернулся.

Пара разбора держится **кто бы ни вёл обход.** Разбирать дерево руками —
поддержанное дело, и контейнер может присоединиться к уже идущему обходу вместо
того, чтобы начинать второй; в обоих случаях пути получает не он.
`onDisposalProgress` отправляют, когда диспозер вернулся, а не когда путь дошёл
до колбэка, поэтому пара переживает все три случая. Разбор нельзя отменить:
каждого освобождения дожидаются.

В отличие от `onProgress`, вход **не** передаётся дальше скоупу, которому
принадлежит контейнер, — см. примечание в конце следующего раздела.

### Что несёт `onProgress`

`progress` имеет тип `Object?`, потому что два источника сообщают разное,
и каждое уже типизировано по-своему:

- от скоупа — значение, которое его инициализация сообщила как прогресс: то,
  что приложение передало в `ctx.progress`; в большинстве приложений это
  `String` на заставке;
- от контейнера зависимостей, который инициализируется, —
  `ScopeAutoDependenciesProgress`: он несёт `path` только что построенной
  зависимости, а вместе с ним `name`, `number`, `total` и `value`. `Scope`, чей
  контейнер строит зависимости, передаёт то же значение дальше, поэтому оно
  приходит дважды: под меткой контейнера и под меткой скоупа.

Обернуть эти два в общий тип значило бы выдумать третий.

**Разбор в их число не входит.** Входил: голый `String` с путём только что
освобождённой зависимости приходил сюда же, — и из-за этого один хук значил две
разные вещи в двух разных точках жизненного цикла, а различали их по типу
значения. Теперь у разбора есть свой `onDisposalProgress`. См. «Если вы пришли
с 0.12.x» ниже.

**Отметки входа приходят один раз, а не два.** `onProgress` доходит
и до скоупа, и до контейнера потому, что контейнер передаёт его
в `ctx.progress`. `onStepStarted` и `onDisposalStepStarted` едут собственным
каналом — именно это и позволяет слать их изнутри шага, а не после него, —
поэтому приходят только под меткой контейнера. Наблюдателю, которому они нужны
рядом со скоупом, достаточно прочитать `target`: контейнер отчитывается рядом
со своим скоупом, под собственной меткой.

### `onError` и `ScopePhase`

`phase` говорит, что выполнялось в момент отказа:

| `ScopePhase` | что выполнялось |
| ------------------------------ | ------------------------------------------ |
| `initialization` | инициализация: хук `init()` или фаза |
| `initializationCancellation` | отмена ещё идущей инициализации |
| `build` | сборка собственного поддерева скоупа |
| `preparationForDisposal` | синхронная половина разбора |
| `unmount` | хук `onUnmount` |
| `disposal` | любой `dispose`: `disposeScope`, зависимости, контроллера, `ScopeModel` |
| `abandonedWait` | ожидание, упавшее, когда ждать было уже некому |

Перечисление может пополниться, поэтому `switch` по нему в вашем коде хочет
ветку `default`.

`build` — единственная фаза, кое-что от которой вы увидели бы и без
наблюдателя: на упавшую сборку граница ошибок Flutter отвечает `ErrorWidget`.
Отчёт к этому добавляется, а не встаёт на его место — `ErrorWidget` по-прежнему
появляется, а отказ вдобавок приходит тем же каналом, каким приходит весь
остальной жизненный цикл. Под этой фазой отчитываются пять веток `buildOn*`,
`ScopeWidgetBase.build`, `ScopeModel.build` и `build` у `ScopeState`
и `LiteScopeState`.

`ScopeState` и `LiteScopeState` также сообщают о сбоях `initStateAsync`
и `onInitialized` под фазой `initialization`, с владеющим скоупом в качестве
цели и с сохранением прежнего пути ошибки в зону или Flutter. Обычные хуки
Flutter — например, `initState`, `didChangeDependencies`, `didUpdateWidget`,
`deactivate` и `activate` — остаются вне этого канала наблюдения.

Виджет, который скоупом не является, — нет: `ListenableSelector`
и представления `ScopeNotifier` собираются как любой другой виджет, а `onError`
нужен `ScopeObservable`, которого можно назвать целью. Их сборки остаются
там же, где были, — внутри границы ошибок, и больше нигде.

Разбор, упавший не один раз, сообщает о каждом отказе, а не только о первом.
`Scope` разбирает своё состояние раньше зависимостей, и каждая половина
защищена сама по себе, так что упасть могут обе, и `onError` несёт оба.

Куда такой отказ уходит, кроме наблюдателя, зависит от того, остался ли тот,
кому его можно отдать. Из ошибок, брошенных собственными шагами разбора скоупа,
включая написанный вручную `ScopeDependencies.dispose`, первая доходит до того,
кто запросил разбор, — `close()`, например, — а остальные сообщаются. И ничего
не бросается, пока фреймворк снимает скоуп с дерева: вызывающий там — цикл,
разбирающий целую партию элементов, без границы вокруг любого из них
и по списку, который он уже очистил, — так что бросок оттуда стоил бы каждому
скоупу за этим ровно того разбора, который ему обещан. Оба канала отказ всё
равно несут; броском не является ни один из них.

`ScopeAutoDependencies.dispose` не бросает дальше ошибку своего дерева.
О каждом упавшем шаге разбора сообщается через `FlutterError.reportError`
там же, где он упал, один раз, а его `onError` несёт отказ, названный путём
шага, и говорит `ScopeErrorRoute.flutterError`, — так что дерево с двумя
упавшими листьями даёт два отчёта. Шаг, упавший с `Cancelled`, говорит
`ScopeErrorRoute.cancellation`, и о нём не сообщается. Успешный `await close()`
поэтому не доказывает, что каждая автоматическая зависимость успешно
освобождена. Каждый упавший шаг доступен через
`flattenDependenciesWithErrors()` и `onError`. Группа, упавшая прежде, чем
дошла до какого-либо ребёнка, — не шаг, и наблюдателю о ней не говорят. О ней
сообщается, когда это первый отказ обхода; за другим отказом она остаётся
только в состоянии дерева, в `flattenDependenciesWithErrors()`.

### `onError` и `ScopeErrorRoute`

Наблюдатель, который шлёт каждый `onError` в трекер падений, о многих отказах
сообщает дважды. Об отказе, который отдать больше некому, — о разборе, упавшем
после того, как скоуп ушёл с дерева, о сборке, которая бросила, — сообщается
ещё и через `FlutterError.reportError`, а сбор падений приложения обычно
слушает и `FlutterError.onError`. `route` говорит, куда ещё уходит отказ,
и к вызову `onError` это уже известно:

| `ScopeErrorRoute` | у кого ещё отказ | например |
| --- | --- | --- |
| `observer` | ни у кого: о нём сказано только наблюдателю | бросивший `initScope`, в том числе с `Cancelled`, или бросивший `initDependencies`; отказ дочерней задачи, который тело поймало или который никто не прочёл |
| `flutterError` | у `FlutterError.onError` — через отчёт пакета или границы ошибок сборки Flutter | бросившая сборка или синхронный `init()`; отказ разбора, когда вызывающего не осталось; позднее освобождение; упавшие очистка, колбэк или поздняя работа задачи инициализации |
| `zone` | у зоны, в которой работает скоуп, как необработанная ошибка | бросивший `initStateAsync` у `LiteScopeState` или `ScopeState`; `AsyncScope`, упавший до начала инициализации |
| `caller` | у кода, вызвавшего `close()`: его `Future` завершается с отказом | первый отказ разбора, который начал `close()` |
| `cancellation` | ни у кого, потому что это не отказ | `Cancelled`, брошенный очисткой или колбэком задачи инициализации либо шагом разбора дерева зависимостей; ошибка, которую `Job.isCancellationError` называет отменой у отменённой задачи |

Так что трекер падений передаёт дальше `ScopeErrorRoute.observer` и больше
ничего, как это делает `CrashReporter` выше, и о каждом отказе сообщается один
раз. `caller` — ваш собственный код: тот, кто вызвал `close()`, получает отказ
и сообщает о нём, если хочет. Перечисление тоже может пополниться, и `switch`
по нему хочет ветку `default`.

`ScopeConfig.observer`, оставленный в `null`, не прячет ни одного отказа
целиком. Упавшая инициализация по-прежнему видна в `buildOnError`, а отказ
дочерней задачи, который никто не прочёл и который при наблюдателе достаётся
одному наблюдателю, вместо этого сообщается через `FlutterError.reportError`.

Маршрут окончателен в момент вызова `onError`, и всё же в девяти случаях он
говорит не всё:

- **`close()`, присоединившийся к разбору, который начало дерево.** Скоуп,
  снятый с дерева, уже начал разбор, так что первый отказ этого разбора говорит
  `flutterError`, и о нём сообщается. `close()`, вызванный у скоупа после
  этого, разделяет тот же разбор, и `Future`, который он возвращает,
  завершается тем же отказом. Код, который сообщает о том, что бросил его
  `close()`, сообщит об этом отказе второй раз;
- **дерево зависимостей, разбираемое вручную.** `root.dispose()` у дерева
  `ScopeAutoDependencies` обходит его так же, как это делает контейнер:
  о каждом упавшем шаге сообщается, и каждый говорит `flutterError`, первый
  тоже, — а первый `root.dispose()` ещё и бросает вам. О нём уже сообщено, так
  что коду, который ведёт обход, сообщать о брошенном не нужно;
- **группа, упавшая за другим отказом.** Группа дерева зависимостей, упавшая
  прежде, чем дошла до какого-либо ребёнка, — не шаг: ни один шаг о ней
  не сообщает, и наблюдателю о ней не говорят. Когда это первый отказ обхода,
  контейнер сообщает о ней как об отказе, который выходит из обхода. Когда
  первым был другой отказ, из обхода выходит он, а отказ группы остаётся только
  в состоянии дерева: он есть в `flattenDependenciesWithErrors()`, но его нет
  ни в `onError`, ни в `FlutterError.onError`;
- **`Cancelled`, брошенный хуком разбора скоупа**, например `disposeScope` или
  `onUnmount`. Он говорит `flutterError`, и о нём сообщается, как о любом
  другом отказе этого этапа. Трекер падений, который слушает
  `FlutterError.onError`, получает его как отказ;
- **`ignoreFailure()`, вызванный поздно у отменённого ребёнка.** Дочерняя
  задача, чьё тело падает уже после её отмены, говорит `flutterError`, и отчёт
  приходит, когда задача закончилась. `child.ignoreFailure()`, вызванный вашим
  кодом в промежутке — после отказа, до конца задачи, — этот отчёт отнимает.
  Тогда отказ достаётся одному наблюдателю, под маршрутом, который говорит
  иное, и трекер падений, передающий дальше `observer`, его так и не увидит;
- **отказ, который ваше приложение называет отменой, брошенный до отмены.**
  Когда тело инициализации падает, пока очистка, которую оно зарегистрировало,
  ещё идёт, а скоуп снимают с дерева раньше, чем эта очистка закончится, исход
  перехватывает отмена: тогда отказ говорит `flutterError`
  с `ScopePhase.initializationCancellation`, и о нём сообщается. Если же
  `Job.isCancellationError` называет этот отказ отменой, `onError` для него
  не вызывается вовсе — даже с `cancellation`. Наблюдатель, который считает
  отказы, его не увидит;
- **два одинаково закончившихся отказа и два маршрута.** Отказ тела, перекрытый
  отменой, как выше, говорит `flutterError`. Отказ дочерней задачи, который
  тело выпустило и который отмена перекрыла так же, говорит `observer`
  с `ScopePhase.initialization`: наблюдатель услышал его от ребёнка раньше, чем
  что-либо решилось, ему сказали, что больше отказ никуда не уходит, и о нём
  не сообщается, если только тело не возьмётся за него снова после своей отмены
  (следующий случай). При передаче по маршруту о каждом сообщается один раз,
  но журнал или тест, который ждёт оба в `FlutterError.onError`, найдёт там
  только первый;
- **один объект, упавший дважды.** Пакет различает отказы по идентичности, так
  что `const`-исключение — `throw const NetworkUnavailable()` — или
  закешированная ошибка, брошенная снова, для него один отказ, сколько бы раз
  его ни бросили. Наблюдатель слышит его один раз, с первым маршрутом. Если
  отказ дочерней задачи сказал `observer`, а потом тем же объектом падает
  очистка, колбэк или поздняя работа задачи инициализации либо само тело после
  того, как скоуп убрали с дерева, — прочтя ребёнка или снова бросив
  пойманное, — то, будь это тот же отказ, брошенный снова, или второй, о нём
  сообщается ещё и через `FlutterError.reportError`, а наблюдателю второй раз
  не говорят. Лишний отчёт лучше потерянного: трекер падений, который передаёт
  дальше `observer` и слушает `FlutterError.onError`, получит этот отказ
  из обоих мест;
- **наблюдатель есть, даже когда он ничего не делает.** Отказ дочерней задачи,
  который никто не прочёл, говорит `observer` и не попадает в `FlutterError`,
  когда `ScopeConfig.observer` задан, если не считать случая выше: пакет
  не смотрит, что за ним. Пустой `ScopeCompositeObserver` не пускает отказ туда
  точно так же, и тогда он не достаётся никому. При `ScopeConfig.observer`,
  равном `null`, о нём сообщается, и так же — когда бросает `onError` самого
  наблюдателя: такой наблюдатель ничего не услышал. А вот
  `ScopeCompositeObserver` услышал всегда: он сам ловит то, что бросил
  наблюдатель внутри него, и сообщает об этом, так что отказ в `FlutterError`
  не попадает, и если бросил как раз трекер падений, отказ не достаётся никому.

### Что покрывает `onTimeout`

Об истечении через наблюдателя сообщает каждое ограниченное ожидание — все
семь, — и `what` называет то, которое истекло:

| `what` | какое ожидание |
| --- | --- |
| `access to its scopeKey` | скоуп стоит в очереди за предыдущим на том же ключе |
| `its own teardown` | скоуп ждёт `disposeScope` |
| `its state to be disposed of` | первая половина этого ожидания у `Scope`, у которого их две |
| `its dependencies to be disposed of` | и вторая половина |
| `its initialization to be cancelled` | разбор пришёл, когда инициализация ещё шла |
| `its controller to be released` | `AsyncControllerScope` возвращает контроллер, который его собственная инициализация так и не передала дальше |
| `its child scopes` | родитель ждёт скоупы под собой |
| `the disposal` | контейнер зависимостей ждёт освобождения построенного им дерева |

`error` — это та самая `TimeoutException`, которую несёт отчёт: имя скоупа,
лимит и — у двух ожиданий, которые стоят за кем-то в очереди, — то, что не было
завершено в момент истечения: записи впереди в очереди `scopeKey` или дети,
конца которых родитель так и не дождался. Это всё, что пакет знает
об истечении, так что наблюдателю, который его логирует, больше ничего
не нужно.

Об истечении никогда не сообщают одним только наблюдателем. Первые два доходят
ещё и до собственных колбэков скоупа — `onScopeKeyTimeout`
и `onWaitForChildrenTimeout`, — а каждое из шести сообщается через
`FlutterError.reportError`, если только его место не занял ваш колбэк или
приложение не выключило эти отчёты. Ни колбэк, ни переключатель этого события
не касаются: наблюдатель — то, что пакет сообщает о себе, а не ваша обработка
ошибок.

### Что покрывает `onTrace`

Всё, что лежит под жизненным циклом: подготовка к инициализации и к разбору,
очередь `scopeKey` (ожидание доступа, его получение, отказ от него, выход),
ожидание дочерних скоупов, ожидание конца инициализации, две точки внутри
зависимости, где разбирается ошибка, и сообщения, которые инициализация
посылает через `ctx.log`.

Скоуп даёт с десяток таких событий там, где даёт одно любое другое, — поэтому
`ScopePrintObserver` их не печатает. Это то, что включают, когда скоуп
подвисает, инициализируется в неожиданном порядке или утилизируется слишком
поздно, и больше ни для чего.

## О ком событие

Первый аргумент каждого хука — `ScopeObservable`, и единственный его член —
имя, которым источник себя называет:

| источник | `debugLabel` |
| ----------------------------- | ------------------------------------------ |
| элемент любого скоупа | `CounterScope(#4e0b7)` или `CounterScope(cart)` |
| контейнер зависимостей | `AppDependencies(#25f53)` |
| одна зависимость | её объявленное имя; `[group]`, если группа анонимна |

Поэтому `tag` — самый дешёвый способ отличить в выводе два скоупа одного типа
и единственный способ получить метку, одинаковую от прогона к прогону: короткий
хеш таким не бывает.

`ScopeObservable` намеренно не реализуют `ScopeDependencies`
и `ScopeDependency`: их пишете вы, и новый обязательный член сломал бы уже
написанный код. События порождают только классы пакета, поэтому маркер несут
только они.

Наблюдатель, которому нужен один вид источника, сужает шаблоном,
а не приведением:

```dart
final class ScopeAnalytics extends ScopeObserver {
  const ScopeAnalytics();

  @override
  void onReady(ScopeObservable target) {
    if (target case ScopeInheritedElement(:final widget)) {
      analytics.logEvent('scope_ready', {'type': '${widget.runtimeType}'});
    }
  }
}
```

## ScopePrintObserver

Наблюдатель, который едет в комплекте, пишет по строке на событие:

```dart
ScopeConfig.observer = const ScopePrintObserver();
```

```text
scopo | CounterScope(#4e0b7) | initialize…
scopo | AppDependencies(#25f53) | progress: prefs (1/2)
scopo | CounterScope(#4e0b7) | initialized
scopo | CounterScope(#4e0b7) | initialization failed: Exception: no network
```

Форма строки — `scopo | <метка> | <что случилось>`. Отказ добавляет
`: <ошибка>`, а если событие несёт стек вызовов — и его, отдельной строкой.

Фаза отказа проговаривается по-английски, а не именем значения `ScopePhase`:
`initialization failed`, `initialization cancellation failed`, `build failed`,
`preparation for disposal failed`, `unmount failed`, `disposal failed` и —
единственная, что не влезает в эту форму, —
`an abandoned wait ended in a failure`.

Два параметра, оба необязательные:

```dart
ScopeConfig.observer = ScopePrintObserver(
  output: debugPrint,
  trace: true,
);
```

`output` — куда уходит строка; по умолчанию `print`. `trace` решает,
печатается ли `onTrace` вообще, и по умолчанию `false` — это и есть всё, что
раньше делал здесь порог уровней.

Конструктор `const`, а наблюдатель выше — нет: `debugPrint` — переменная,
которую Flutter разрешает подменять, то есть не константа. С `output`
по умолчанию и со своей функцией, которая константа, `const` работает.

## Когда падает сам наблюдатель

Наблюдатель — ваш код, и пакет зовёт его из сборки, из инициализации
и из разбора. Хук, упавший наружу из любого из трёх, унёс бы скоуп с собой:
скоуп, который так и не построил готовую ветку, или разбор, остановившийся
на полпути с удержанным `scopeKey`.

Поэтому каждый вызов идёт через защиту. Упавший хук сообщается через
`FlutterError.reportError` с `library: 'scopo'` — красный экран в debug,
`FlutterError.onError` в release, — а то, что сообщало о событии, продолжается.
Ничего не проглатывается и ничего не повторяется.

Та же защита отбивает повторный вход. Наблюдатель, который порождает событие
скоупа, пока его оповещают, — например, монтирует скоуп прямо из хука, — иначе
ушёл бы в бесконечную рекурсию; второе оповещение отбивается и репортится —
по одному разу на каждый отбитый вызов, — а первое доходит до конца.

## Таймауты

Четыре вида ожиданий в жизненном цикле скоупа ограничены таймаутом, и все
четыре значения по умолчанию живут в `ScopeConfig`:

- `ScopeConfig.defaultScopeKeyTimeout` — сколько скоуп ждёт, пока предыдущий
  владелец освободит его `scopeKey`;
- `ScopeConfig.defaultInitCancellationTimeout` — сколько разбор ждёт отмены
  инициализации;
- `ScopeConfig.defaultDisposeScopeTimeout` — сколько разбор ждёт
  `disposeScope`, собственного освобождения скоупа;
- `ScopeConfig.defaultWaitForChildrenTimeout` — сколько скоуп ждёт утилизации
  дочерних скоупов, прежде чем утилизироваться самому.

Семь строк и восемь ярлыков: у `Scope` за `disposeScope` стоят два шага,
и каждый ограничен отдельно, — поэтому он сообщает одну из двух средних строк,
а не `its own teardown`, который сообщают все остальные семейства.

Все четыре по умолчанию три секунды. `null` снимает ограничение, и ждать
бесконечно будет каждый скоуп; то же делает и `ScopeTimeout.none` — значение
ниже, которым отдельный скоуп говорит то же самое про себя, и которое здесь
тоже принимают. Истёкший таймаут не фатален: о нём сообщают через
`FlutterError.reportError`, после чего скоуп продолжает так, будто ожидание
удалось, — поэтому зависимость, которая никогда не завершает свою утилизацию,
вырождается в задержку плюс сообщение об ошибке, а не в дедлок.

**`ScopeConfig.timeoutReportsEnabled = false` выключает отчёт — и только
отчёт.** Ожидание по-прежнему сдаётся вовремя, скоуп по-прежнему идёт дальше,
четыре колбэка по-прежнему зовут, а наблюдатель по-прежнему слышит истечение —
и слышит его с той самой `TimeoutException`, которую нёс бы отчёт, так что,
забрав отчётность себе, вы ничего не теряете. Это для приложения, которое
сообщает об истечениях из собственного наблюдателя: одно истечение, пришедшее
дважды — событием и ошибкой Flutter, — и есть то, из-за чего одно из двух
выглядит отдельной проблемой.

Ещё два ожидания берут одно из этих умолчаний. Первое своего переопределения
не имеет. Когда инициализация `Scope` проваливается, контейнер зависимостей
освобождает то, что успел построить, и это освобождение ограничено
`ScopeConfig.defaultDisposeScopeTimeout`, а не `disposeScopeTimeout` скоупа:
контейнер ничего не знает о виджете, которому принадлежит, и работает без него,
поэтому читать значение отдельного скоупа там неоткуда. Ограничено оно вообще
потому, что это путь провалившейся инициализации: ниже по течению провал никто
не увидит, пока контейнер не отпустит, — и диспозер, который не завершается,
оставляет скоуп над ним показывать ветку загрузки, без единой строки на экране
и в консоли.

Второе — вторая половина разбора самого `Scope`, и переопределение оно берёт.
`disposeScope` там один метод и два шага: собственный разбор состояния,
а за ним разбор контейнера, — и каждый ограничен своим `disposeScopeTimeout`,
а не тем, что от него оставил другой. Поэтому разбор, в котором зависли оба
шага, сообщает **два** истечения и дважды зовёт `onDisposeScopeTimeout`:
сдались два шага. У всех остальных семейств за этим методом один шаг и один
предел вокруг него.

Все четыре меряются по настоящему времени, а не по часам той зоны, в которой
идёт разбор, — виджет-тест подменяет их фальшивыми. Зависания, ради которых эти
лимиты и нужны, живут дольше кадров, а скоуп обычно снимают между кадрами:
таймер, принадлежащий такой зоне, остался бы непогашенным к моменту, когда
дерева уже нет, а именно на этом `flutter_test` заканчивает тест. Поэтому
собственный тест, которому надо дождаться истечения такого лимита, ждёт
по настоящему времени: `pump(duration)` двигает фальшивые часы и ни до одного
из них не достаёт.

`pauseAfterInitialization` — исключение, и намеренное: эту задержку видит
пользователь, поэтому виджет-тест управляет ею через `pump(duration)`, как
любой анимацией. А скоуп, снятый с дерева посреди паузы, её гасит.

Любой скоуп может переопределить все четыре значения для себя параметрами
`scopeKeyTimeout`, `initCancellationTimeout`, `disposeScopeTimeout`
и `waitForChildrenTimeout` и заметить истечение через колбэки
`onScopeKeyTimeout`, `onInitCancellationTimeout`, `onDisposeScopeTimeout`
и `onWaitForChildrenTimeout`. `null` там означает «взять значение
по умолчанию», а не «ждать сколько понадобится», — второе говорят через
`ScopeTimeout.none`:

```dart
AsyncScope(
  waitForChildrenTimeout: ScopeTimeout.none,   // этот скоуп дождётся
  disposeScopeTimeout: const Duration(seconds: 5),
  …
)
```

Это `Duration` особого вида, а не значение, которое надо помнить, поэтому все
эти параметры остаются `Duration?` и больше в них ничего не меняется.
`AsyncScopeCoordinator.waitForChildren` и собственный `waitForChildren`
родителя тоже его принимают — на один вызов, — и четыре умолчания `ScopeConfig`
выше тоже.

«`Duration` особого вида» — это же и единственное, что о нём надо знать: его
узнают по типу, поэтому вычислений он не переживает.
`ScopeTimeout.none == const Duration(microseconds: -1)` — это `true`,
а `ScopeTimeout.none + Duration.zero` — обычный `Duration`: из любой арифметики
возвращается отрицательная длина, спрятанная за маркером, а её таймер читает
как «истечь немедленно». Пакет ассертит против отрицательного предела везде,
где предел разрешается, поэтому в debug это громко, а не тихо; но таймаут —
всё же значение, которое передают дальше, а не то, с которым считают.

**`initCancellationTimeout` его отвергает**, ассертом. Отмена ждёт, пока
инициализация закончится, а запаркованная на никогда не завершающемся future
не закончится никогда — безлимитное ожидание там и есть тот зависон, ради
которого предел заводили. Снять этот предел — решение для всего приложения,
и принимают его через `ScopeConfig.defaultInitCancellationTimeout`: либо
`null`, либо тот же `ScopeTimeout.none`, который там значит то же самое. Ассерт
срабатывает внутри собственной охраны этой стадии разбора, поэтому приходит как
`onError` с `ScopePhase.initializationCancellation`, а разбор продолжается.

**`pauseAfterInitialization` отвергает его тоже**, своим ассертом,
и по обратной причине: пауза — это отрезок времени, на который придерживают
ready-ветку, а не предел ожидания, и «ждать сколько понадобится» про неё ничего
не говорит. Этот ассерт срабатывает, пока скоуп становится готовым, поэтому
приходит как `onError` с `ScopePhase.initialization`, а скоуп показывает ветку
ошибки.

## pauseAfterInitializationEnabled

`pauseAfterInitialization` — искусственная задержка между моментом, когда скоуп
стал готов, и моментом, когда показывают его поддерево; она существует, чтобы
индикатор загрузки провисел достаточно долго, чтобы его успели прочитать,
а не мигнул.

`ScopeConfig.pauseAfterInitializationEnabled = false` выключает все такие паузы
глобально, не трогая объявившие их виджеты. Ставьте это в настройке
виджет-теста или когда проходите инициализацию отладчиком.

## reset()

Перечисленные выше переключатели — пауза и четыре таймаута — глобальные и живут
дольше кода, который их менял: тест, поднявший таймаут и забывший вернуть его
на место, отдаёт следующему тесту другой пакет. `ScopeConfig.reset()`
возвращает все пять к умолчаниям:

```dart
void main() {
  tearDown(ScopeConfig.reset);
  …
}
```

`setUp` подходит не хуже и вдобавок покрывает тест, упавший до собственного
teardown. Наблюдателя это не трогает: он объект, а не переключатель, и обычно
он и есть смысл того прогона, ради которого его поставили. Сьюта, которой он
нужен убранным, убирает его сама — `ScopeConfig.observer = null`.

## В тестах

Наблюдатель, который записывает вместо того, чтобы печатать, превращает
жизненный цикл в значение, о котором тест может делать утверждения. Сравнивайте
список целиком: так ловится и пропущенное событие, и лишнее, чего проверка
каждого события по отдельности не даёт.

```dart
final class RecordingObserver extends ScopeObserver {
  final events = <String>[];

  @override
  void onInit(ScopeObservable target) =>
      events.add('init ${target.debugLabel}');

  @override
  void onReady(ScopeObservable target) =>
      events.add('ready ${target.debugLabel}');

  @override
  void onDisposed(ScopeObservable target) =>
      events.add('disposed ${target.debugLabel}');
}

void main() {
  late RecordingObserver observer;

  setUp(() {
    observer = RecordingObserver();
    ScopeConfig.observer = observer;
    ScopeConfig.pauseAfterInitializationEnabled = false;
  });

  tearDown(() {
    ScopeConfig.observer = null;
    ScopeConfig.reset();
  });

  testWidgets('скоуп инициализируется один раз и один раз утилизируется',
      (tester) async {
    await tester.pumpWidget(const CounterScope(tag: 'counter'));
    await tester.pumpAndSettle();
    await tester.pumpWidget(const SizedBox());
    await tester.pumpAndSettle();

    expect(observer.events, [
      'init CounterScope(counter)',
      'ready CounterScope(counter)',
      'disposed CounterScope(counter)',
    ]);
  });
}
```

Две вещи, от которых это ожидание зависит. Скоуп с тегом — потому что скоуп без
тега называет себя коротким хешем, а он от прогона к прогону другой: ставьте
`tag` или срезайте `(…)` с метки перед сравнением. И наблюдатель убирается
в teardown — потому что `ScopeConfig.reset()` его не убирает: оставленный
наблюдатель продолжит писать в список следующего теста.

Не включайте `trace`, если тест не про трассировку. На этом уровне один скоуп
даёт с десяток событий, и ожидание, перечисляющее их все, падает от любой
посторонней правки в координации.

Настройку настоящего приложения смотрите
в [example/minimal](https://github.com/vi-k/scopo/blob/main/example/minimal/lib/main.dart),
а демонстрацию, где рядом видны все вызовы жизненного цикла всех семейств
скоупов, —
в [example/scopo_demo](https://github.com/vi-k/scopo/tree/main/example/scopo_demo).

## Если вы пришли с 0.12.x

**Контейнер зависимостей больше не отчитывается о разборе через `onProgress`.**
Освобождение каждой зависимости приходит в `onDisposalProgress(target, path)`,
а шаг, которому оно принадлежит, объявляется перед ним через
`onDisposalStepStarted(target, path)`.

Существующий `onProgress` продолжает компилироваться, и в этом неудобство
именно этой правки: он по-прежнему переопределяет существующий метод — просто
для разбора его больше не зовут, и ничто на это не указывает. Если вы различали
половины по типу `progress`, эта ветка стала хуком:

```dart
// было
final class BeforeObserver extends ScopeObserver {
  @override
  void onProgress(ScopeObservable target, Object? progress) {
    if (progress is String) {
      log('освобождено $progress');
    } else {
      log('построено $progress');
    }
  }
}

// стало
final class AfterObserver extends ScopeObserver {
  @override
  void onProgress(ScopeObservable target, Object? progress) =>
      log('построено $progress');

  @override
  void onDisposalProgress(ScopeObservable target, String path) =>
      log('освобождено $path');
}
```

`ScopeCompositeObserver` и `ScopePrintObserver` идут в составе пакета
и изменены вместе с ним; смотреть надо только на собственного наблюдателя.

**Один случай, когда этот релиз не промолчит, а уронит сборку.**
В `ScopeObserver` добавлены три имени, а перегрузки в Dart нет: подкласс,
у которого уже есть собственный член с именем `onStepStarted`,
`onDisposalStepStarted` или `onDisposalProgress`, объявляет теперь некорректное
переопределение. Случай редкий — для вспомогательного метода это не очевидные
имена, — но это ошибка компиляции, а не смена поведения: анализатор назовёт её
сам, и переименование члена всё решает.

## Если вы пришли с 0.9.x

Девять публичных имён, построенных на `logger_builder`, удалены:
`ScopeConfig.logger`, `ScopeLogger`, `ScopeLevelLogger`, `ScopeLog`,
`ScopeLogPublisher`, `ScopeLogFormatter`, `ScopeLogTransformer`,
`ScopeLogLevel` и `ScopeLogCallback`. Пакет больше не зависит
от `logger_builder`.

Чем было каждое из них:

- `ScopeConfig.logger.level = ScopeLogLevel.info` →
  `ScopeConfig.observer = const ScopePrintObserver()`;
- `ScopeLogLevel.debug` → `const ScopePrintObserver(trace: true)`;
- `ScopeLogLevel.off` → `ScopeConfig.observer = null`;
- публикатор, который форматировал и печатал, → `output` у `ScopePrintObserver`
  или свой `ScopeObserver`;
- публикатор, который собирал записи в список для проверок, → наблюдатель,
  который записывает, как в разделе «В тестах» выше;
- трансформер, выбрасывавший записи одного пути, → `if` внутри хука,
  по `target.debugLabel` или по типу `target`;
- отправка отказов дальше через разбор `ScopeLog.message` → `onError`, где
  ошибка, стек вызовов и `ScopePhase` уже разделены.

Порога больше нет, и ничего одного вместо него не появилось. Его три задачи
разошлись: `ScopeConfig.observer = null` выключает всё, пустое тело хука
выключает один вид событий, а `trace` — самый шумный из них.
