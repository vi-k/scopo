# base

> Перевод `doc/base.md` (blob `9a6044a5e25d88291cc36d1be32241e77e62bd73`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Каждое семейство скоупов этого пакета — `ScopeWidgetBase`, `ScopeModel`,
`ScopeNotifier`, `AsyncScope`, `AsyncDataScope`, `AsyncControllerScope`,
`LiteScope` и `Scope` — стоит на одних и тех же трёх типах. Вместе они говорят,
что такое скоуп для дерева виджетов: `InheritedWidget`, который можно найти
снизу, элемент, владеющий тем, что скоуп держит, и один протокол поиска, общий
для всех.

| тип | что это |
| --- | --- |
| `ScopeInheritedWidget` | `InheritedWidget`, от которого происходит виджет любого скоупа |
| `ScopeContext` | протокол поиска: `of`, `maybeOf`, `select` |
| `ScopeInheritedElement` | что обязан предоставить элемент скоупа |

Приложение их не создаёт. Читать этот слой всё же стоит, и по двум причинам:
здесь решается разница между `of`, `select` и `listen: false` — одинаково
во всех семействах, — и здесь же лежит контракт, который реализуют, когда пишут
свой скоуп.

## Виджет

```dart
abstract base class ScopeInheritedWidget extends InheritedWidget {
  final Object? tag;

  const ScopeInheritedWidget({super.key, this.tag, super.child});
}
```

`tag` называет конкретный скоуп. Два скоупа одного типа иначе неразличимы
в выводе, где скоуп без тега выглядит как `CounterScope(#4e0b7)`, а с тегом —
как `CounterScope(cart)`; формат описан в теме `debug`. Параметр `tag`
пробрасывает в этот конструктор каждое семейство, так что тег можно повесить
на любой скоуп.

Про `child` нужно предупредить отдельно: это не то, что скоуп показывает.
Обычный `InheritedWidget` оборачивает переданное ему поддерево; скоуп строит
своё через `buildChild()` — отсюда берутся ветки ожидания, инициализации,
ошибки и закрытия у старших семейств. Конструктор всё же принимает `child`,
поэтому семейство, которому нужно обычное поведение, может его передать
и использовать из `buildChild()`; в пакете так не делает никто. Значение
по умолчанию — заглушка, которая отказывается создавать элемент вовсе: если
скоуп всё-таки построит этот `child` вместо своего, поломка будет немедленной,
а не незаметной.

## Элемент

```dart
abstract interface class ScopeInheritedElement<W extends ScopeInheritedWidget>
    implements ScopeContext<W> {
  W get widget;

  @mustCallSuper
  void init();

  @mustCallSuper
  void dispose();

  Widget buildChild();
}
```

`init()` выполняется один раз, после монтирования элемента и до его первого
`buildChild`. Если он бросает исключение, для скоупа это конец: хук больше
не вызывают, скоуп показывает ошибку вместо своего поддерева, и каждая
следующая сборка сообщает ту же ошибку. `dispose()` вызывается при снятии
элемента с дерева, и после неудачного `init()` тоже — попытка, сорвавшаяся
на полпути, могла уже что-то взять, и отдаётся это здесь, поэтому утилизатор
семейства обязан быть готов к частично инициализированному скоупу. Оба помечены
`@mustCallSuper`: семейство, которое их переопределяет, продолжает жизненный
цикл, а не подменяет его. Смонтированный элемент уже подключён к предкам,
поэтому из `init()` можно найти скоуп-предок с `listen: false`; подписка
из этого хука не поддерживается, и об этом говорит `assert`. Всё, чем скоуп
владеет, — модель, подписка на notifier, контейнер зависимостей, место
в очереди `scopeKey`, — берётся в первом и освобождается во втором.

Элемент заодно является `ScopeContext` собственного скоупа: именно этот объект
получает потомок из `of`, и поэтому `select` умеет читать текущее значение
прямо из него.

Весь учёт за этим — подписки по каждому зависимому, перестроение, которое
только уведомляет вместо перестроения поддерева, — живёт
в `ScopeWidgetElementBase` и описан в теме `ScopeWidget`. Реализовывать
`ScopeInheritedElement` с нуля не предполагается; предполагается наследоваться
от того класса.

## Поиск скоупа

Три входа, все статические на `ScopeContext`, где `W` — тип виджета, а `C` —
тип контекста семейства:

```dart
ScopeContext.maybeOf<W, C>(context, listen: false); // C?, null, если не найден
ScopeContext.of<W, C>(context, listen: false);      // C, бросает, если не найден
ScopeContext.select<W, C, V>(context, selector);    // V, бросает, если не найден
```

На практике их зовут через обёртку, которую предоставляет каждое семейство, —
так параметры типов остаются короткими и верными:

```dart
final config = ScopeWidgetBase.of<ApiConfig>(context, listen: false);
final apiKey = ScopeWidgetBase.select<ApiConfig, String>(
  context,
  (widget) => widget.apiKey,
);
```

Сам поиск — это `getElementForInheritedWidgetOfExactType<W>()`: только предки
и **точный** тип. Скоуп, объявленный как `class CartScope extends ShopScope`,
по запросу `ShopScope` не найдётся. Поиск сам по себе ничего не перестраивает;
на что подписывается вызывающий, решает аргумент ниже.

## listen и его цена

`listen: false` находит скоуп и не подписывается ни на что. Вызывающего никогда
не перестроят из-за этого скоупа. Это то, что нужно коду вне `build`:
обработчику кнопки, который тянется к сервису, колбэку, который один раз читает
текущее состояние:

```dart
onPressed: () => ScopeModel.of<Cart>(context, listen: false).clear(),
```

`listen: true` подписывает на **любое** изменение этого скоупа. Зависимого
перестраивают всякий раз, когда скоуп уведомляет, независимо от того,
изменилось ли то, что зависимый читает.

`select` подписывает на одно значение и является причиной, по которой скоуп
дёшево обслуживает большое поддерево. Параметра `listen` у него нет — выбирать
и значит слушать, — и нет варианта с `maybe`: отсутствующий скоуп здесь ошибка,
а не `null`.

## Что на самом деле делает select

```dart
final userName = ScopeModel.select<Session, String>(
  context,
  (session) => session.userName,
);
```

Селектор выполняется сразу, а пара `(значение, селектор)` сохраняется как
подписка зависимого. Когда скоуп потом уведомляет, каждая сохранённая пара
каждого зависимого вычисляется заново: зависимого перестроят, только если
хотя бы для одной из них `selector(scope) != value`. Виджет, выбравший
`userName`, проспит изменение `cartTotal`.

Пять следствий стоит держать в голове.

**Сравнение идёт через `!=`**, то есть всё решает `==` выбранного значения.
Выбирайте поле, запись или неизменяемое значение. Селектор, который на каждом
вызове собирает новый `List` или новый объект, всякий раз оказывается не равен
прежнему, и виджет перестраивается так, будто ничего не выбирал.

**Селекторы накапливаются.** Несколько вызовов `select` в одном `build` создают
несколько подписок, и изменение в любой из них перестроит виджет один раз. Три
поля модели — это три `select`, а не один селектор, возвращающий три значения
списком: почему список хуже, сказано выше.

**`of(..., listen: true)` перебивает любой `select` в том же `build`.** Он
подписывает на всё, а подписку на всё нельзя сузить, добавив к ней селектор, —
в любом порядке виджет окажется перестраиваемым на каждое уведомление. Для
одного скоупа в одном `build` выбирайте что-то одно.

**Захваченное значение обновляется на каждой сборке.** Подписки устанавливаются
заново, пока зависимый строится, как и везде во Flutter, — так что скоуп
сравнивает с парой из последней сборки зависимого, а не из первой.

**Подписку можно брать только из сборки**, и об этом говорит ассерт —
`FlutterError`, у которого эта самая фраза стоит заголовком, под ней объяснение
и совет, а в конце назван сам провинившийся зависимый: так же фреймворк
сообщает и о собственном не вовремя сделанном поиске. То, что запросил
зависимый, помнится в разрезе сборки, а граница между сборками взята по кадру —
хука «зависимый сейчас начнёт строиться» у Flutter нет. Поэтому регистрация,
сделанная вне сборки, попадает к той сборке, с которой делит кадр, и стирается
первой сборкой, которая кадр не делит: `didChangeDependencies` идёт в том же
кадре, что и следующая за ним сборка, — `select` оттуда выглядит работающим
и исчезает на первой же пересборке, пришедшей от родителя, а не от изменения.
Чтобы реагировать на изменение, а не показывать его, держите подписку
в `build`, а из `didChangeDependencies` читайте скоуп с `listen: false`.

**Билдер тоже считается сборкой**, и не только тот, что запускает
`LayoutBuilder`: `OrientationBuilder`, `SliverLayoutBuilder` и item-билдеры
ленивых списков строят поддерево от имени позвавшего их элемента, и то, что
регистрирует `select` оттуда, принадлежит этому элементу. Откуда идёт вызов,
бывает по-разному — layout-колбэк на одном кадре, собственная пересборка
элемента на следующем, — и ни то ни другое сборкой Flutter не называет, поэтому
черта проведена по зависимому: ассерт отвергает подписку, взятую в момент,
когда фреймворк пересобирает самого этого зависимого, и это не его `build`. Это
и есть `didChangeDependencies` — под layout-колбэком и где угодно ещё.
Единственное, что осталось непойманным, — `didUpdateWidget` виджета, который
сам находится под layout-колбэком.

**В release не проверяется ничего из этого.** `debugDoingBuild`,
`BuildOwner.debugBuilding` и `RenderObject.debugActiveLayout` Flutter
выставляет внутри собственных ассертов, так что release-сборка не отличит
сборку от колбэка таймера, — да и сам ассерт в неё не попадает. Там ошибка
молчит: подписка исчезает на какой-то из следующих пересборок, и виджет
перестаёт слышать про значение, которое выбрал.

## Чем отличаются зависимости самого Flutter

**У обычного `InheritedWidget` такого правила нет**, и `didChangeDependencies`
документация `State` прямо называет безопасным местом для
`dependOnInheritedWidgetOfExactType`. И правильно называет: зависимость там —
это членство и ничего больше, зависимый либо в множестве, либо нет, а само
множество очищается только при деактивации элемента. Границы «в разрезе
сборки», из которой можно выпасть, там просто нет, поэтому момент вызова
ничего не решает.

Скоуп хранит не членство, а пару `(значение, селектор)`, а пара верна только
для той сборки, которая её сделала. Значит, её надо заменять от сборки
к сборке, и тот, кто заменяет, обязан знать, к какой сборке относится, — в этом
всё правило выше.

**`InheritedModel` — ближайшее, что есть у Flutter к селектору, и свои аспекты
он копит навсегда.** `InheritedModelElement.updateDependencies` добавляет новый
аспект к тем, что у зависимого уже были, и ничего их не снимает, пока элемент
не уйдёт из дерева. Виджет, спросивший `a` в одной сборке и `b` в следующей,
с этого момента будится обоими — в том числе за ветку, которую он больше
не берёт; а один вызов с `aspect: null` навсегда помечает его зависящим
от всего, что бы он ни выбирал потом. Накопление тихое — зависимый просто
пересобирается чаще, чем нужно, и тем чаще, чем дольше живёт, — поэтому там
за моментом вызова и не следит ассерт: ничего не ломается явно.

Скоуп очищает запрошенное зависимым в начале каждой его сборки, так что будит
его ровно то, что выбрала последняя сборка. Этот сброс и есть то, за что платит
правило выше: регистрация обязана назвать свою сборку, а у сделанной
из `didChangeDependencies` ответа нет.

## Где проводит черту provider

`provider` решает ту же задачу и проводит **две** черты — по одной на каждый
из двух своих способов подписаться. Знать это стоит хотя бы потому, что между
собой они не согласованы и ни одна не совпадает с правилом выше. Всё ниже
прочитано в версии 6.1.5+1.

**`context.watch` и `Provider.of` с `listen: true` охраняются кадром.** Ассерт
спрашивает, строит ли что-нибудь владелец сборки вообще, — это та самая грубая
черта, которую этот пакет когда-то проводил и от которой отказался: она ловит
колбэк кнопки и таймер, но пропускает `didChangeDependencies`, потому что хуки
зависимого бегут в том же `buildScope`, что и сборки вокруг них. Взятый оттуда
`watch` не отвергается.

**`context.select` охраняется зависимым** — так же, как правило выше: ассерт
спрашивает, находится ли вызывающий элемент в собственной `build`, поэтому
`select` из `didChangeDependencies` там отвергается ровно как здесь.
А исключение для layout-колбэка вписано в ассерт **типом виджета**:
`LayoutBuilder` пропускается по имени. Это покрывает `OrientationBuilder` —
он `StatelessWidget` поверх `LayoutBuilder` и отдаёт в свой билдер контекст
того самого элемента; и не покрывает `SliverLayoutBuilder`, который приходится
`LayoutBuilder` не потомком, а братом — вторым наследником
`ConstrainedLayoutBuilder`, — и на проверке, написанной по первому, падает.

**Item-билдер ленивого списка отвергается начисто**, отдельным ассертом, совет
которого — обернуть элемент списка в `Builder` или вынести в отдельный виджет.
Это тот же вопрос, на который здесь отвечено наоборот, и у обоих ответов есть
причина. Контекст, который ленивый список отдаёт своему item-билдеру, — это
элемент **самого списка**, и в том пакете, и в этом; значит, взятый на нём
`select` подписывает список целиком, и изменение пересобирает все ячейки,
которые список держит, а не ту одну, которой оно нужно. От этого совет
и бережёт. Правило здесь пропускает такой код потому, что это обычный рабочий
код, отвергать который debug-сборке незачем, — но дешевле по-прежнему `Builder`
вокруг ячейки, ровно по той причине, которую называет provider.

**Запрошенное зависимым чистится по микротаску, а не по сборке.** provider
держит селекторы одного зависимого множеством и опустошает его на первой
регистрации, пришедшей после границы микротаска, — саму границу он себе
и планирует, когда множество наполняется впервые. Пачка, которую он так
очерчивает, — это «всё, зарегистрированное в одном синхронном отрезке»,
а не «эта сборка этого зависимого». Работает, потому что `select` и так заперт
в сборке, но часы это другие, не те, по которым идёт правило выше.

**А `watch` назад не забрать.** Подписка на всё хранится зависимостью, которая
не является множеством селекторов, и первое, что делает регистрация, — выходит
сразу, обнаружив такую. Зависимый, который однажды сделал `watch`, подписан
на все изменения этого провайдера до конца жизни элемента, что бы он ни
выбирал потом, — та же ловушка, что `aspect: null` у `InheritedModel`. Здесь
`of(..., listen: true)` перебивает `select` только внутри той сборки, где он
взят: следующая начинается с чистого листа.

`Element.dirty` provider читает тоже — на пути уведомления: у зависимого,
которому пересборка уже назначена, гонять селекторы незачем. Комментарий рядом
с этой проверкой говорит то же, что и ассерт здесь: `select` невозможен внутри
`didChangeDependencies`. Один и тот же флаг в разных ролях — там он бережёт
работу, здесь отличает собственную сборку зависимого от билдера, который тот
крутит за кого-то другого.

Все четверо в одной таблице:

| | `InheritedWidget` | `InheritedModel` | `provider` | скоуп |
| --- | --- | --- | --- | --- |
| что хранит зависимость | членство | множество аспектов | множество селекторов либо «всё» | пару `(значение, селектор)` |
| когда очищается | при деактивации | при деактивации | на первой регистрации после микротаска | в начале каждой сборки зависимого |
| подписка на всё | единственный режим | `aspect: null`, навсегда | `watch`, навсегда | действует внутри своей сборки |
| откуда можно брать | откуда угодно, `didChangeDependencies` включительно | откуда угодно | `watch` — из любой фазы сборки; `select` — из своей `build` плюс `LayoutBuilder` по имени | из сборки, черта по зависимому |
| из item-билдера ленивого списка | можно | можно | нельзя; оберните в `Builder` | можно, и подписан будет список |

## Зависимость от себя

Элемент скоупа может подписаться на собственный скоуп — так старшие семейства
перестраивают своё же поддерево по ходу инициализации. `InheritedElement` это
запрещает (ассерт в `notifyClients` блокирует зависимость от себя), поэтому
такие подписки хранятся отдельно от остальных и уведомляются отдельно. Механизм
принадлежит `ScopeWidgetElementBase`; здесь он важен лишь как причина,
по которой `ScopeInheritedElement` — интерфейс, реализуемый семейством,
а не миксин, который подмешивает приложение.

## Ошибки

Обе неудачи — обычные исключения, называющие запрошенный тип:

```text
Exception: CounterScope not found in the context
```

`of` или `select` не нашли виджет выше контекста. Либо скоупа там правда нет,
либо контекст принадлежит виджету над ним, а не под ним — обычная ошибка здесь
это поиск из того самого `build`, который скоуп и устанавливает. `maybeOf`
в той же ситуации вернёт `null` и годится там, где отсутствие ожидаемо.

Поиск с `listen: true`, ничего не нашедший, всё равно запоминается как
зависимость — ровно так же, как его запомнил бы штатный
`dependOnInheritedWidgetOfExactType`. Виджет, спросивший, когда скоупа над ним
не было, и позже перенесённый под скоуп по `GlobalKey`, получит
`didChangeDependencies` и спросит снова.

```text
Exception: The element of ScopeModel<Counter> is not ScopeModelContext<ScopeModel<Counter>, Counter>
```

Виджет нашёлся, но его элемент — не тот тип контекста, который запросили. Это
несовпадение параметров типов: аксессор одного семейства применили к скоупу
другого.

## Аксессоры и шаблоны для редакторов

Каждое семейство находит свой скоуп статическими методами, которые берут
типовые аргументы семейства:
`Scope.select<App, AppDependencies, AppState, V>(context, selector)` и четыре
его соседа. Если писать их обёртками на скоупе, тройка повторяется по пять раз
на скоуп.

У каждого семейства есть и объект-аксессор, который берёт эти аргументы один
раз:

```dart
final class App extends Scope<App, AppDependencies, AppState> {
  static const access = ScopeAccess<App, AppDependencies, AppState>();
}

final counter = App.access.select(context, (state) => state.counter);
```

Это переадресация и ничего больше — каждый метод есть статический метод того же
имени, — так что одно заменяемо другим, а скоуп, которому нужны аксессоры под
своими именами, по-прежнему пишет их сам. Таблица всех восьми — в `README`
пакета.

Шаблон отвечает на ту же цену с другой стороны. Его скелеты выписывают
аксессоры статическими методами скоупа — на месте вызова получается
`App.select(context, …)`, и набирать нечего, потому что набрал шаблон. Одно
другому не соперник: аксессор — для кода, который пишут руками, шаблон — для
кода, который пишут нажатием. Оба едут с пакетом: `ide/scopo.code-snippets` для
VS Code (а также Cursor, Windsurf, Antigravity)
и `ide/scopo-live-templates.xml` для IntelliJ и Android Studio — оба в каталоге
пакета, рядом с `lib/`. Одиннадцать шаблонов: по одному на семейство, два
на контейнер зависимостей (автоматический и рукописный), один на строку
аксессора. Каждый выписывает все классы, которые нужны этой форме, одной
вставкой — разносить их по файлам вам:

```json
"scopo: The accessor object": {
  "scope": "dart",
  "prefix": "scopo-access",
  "body": ["static const access = ScopeAccess<${1:Widget}>();$0"]
}
```

**Как их поставить.** Они едут вместе с пакетом, то есть уже лежат на вашей
машине. Для VS Code — а также Cursor, Windsurf и Antigravity, у них общий
формат, — скопируйте сниппеты в проект:

```sh
mkdir -p .vscode
cp "$(find ~/.pub-cache/hosted/pub.dev -maxdepth 1 -name 'scopo-*' | sort -V | tail -1)"/ide/scopo.code-snippets .vscode/
```

Для IntelliJ IDEA и Android Studio кнопки импорта на странице Live Templates
больше нет. Файл кладут в каталог настроек IDE, в подпапку `templates/`, под
именем группы, которую он объявляет: XML объявляет `scopo`, значит файл —
`scopo.xml`. После этого IDE перезапускают:

```sh
# Android Studio на macOS; для IntelliJ IDEA каталог —
# ~/Library/Application Support/JetBrains/<продукт>/
DIR=~/Library/Application\ Support/Google/AndroidStudio<версия>/templates
mkdir -p "$DIR"
cp "$(find ~/.pub-cache/hosted/pub.dev -maxdepth 1 -name 'scopo-*' | sort -V | tail -1)"/ide/scopo-live-templates.xml "$DIR/scopo.xml"
```

Группа появится в **Settings → Editor → Live Templates**.

Остальное —
в [`ide/README.md`](https://github.com/vi-k/scopo/blob/main/ide/README.md):
таблица всех одиннадцати и то, что о них проверяется. Скелеты, которые эти
шаблоны вставляют, компилируются гейтом пакета, а сьюта держит каждый live
template на его контексте; что сделает с файлом редактор, по-прежнему
показывает только импорт — Android Studio его приняла.

## Куда дальше

| тема | о чём |
| --- | --- |
| `ScopeWidget` | базовый элемент всех семейств: подписки, перестроение-уведомление |
| `ScopeModel`, `ScopeNotifier` | скоупы, владеющие обычным объектом или `Listenable` |
| `AsyncScope`, `AsyncDataScope` | асинхронные инициализация и утилизация |
| `AsyncControllerScope` | скоуп, всё содержимое которого — контроллер с собственным жизненным циклом |
| `LiteScope` | скоуп без контейнера зависимостей |
| `Scope` | полное семейство: зависимости, состояние и четыре ветки сборки |
| `debug` | наблюдатель, таймауты и как выглядит `tag` в выводе |
