# LiteScope

> Перевод `doc/lite_scope.md` (blob `ebbf5277c9dbc07f131dce5104a7cf4585ac67f8`).
> Правится в том же коммите, что и оригинал; проверка — `sh docs/ru/check.sh`.

Класс состояния, за которым стоит весь жизненный цикл скоупа, но перед которым
нет контейнера зависимостей. `initState`, `build` и `setState` работают как
обычно; разбор использует `onUnmount` и ожидаемый `disposeStateAsync` вместо
переопределения `dispose`. Есть также асинхронный `initStateAsync`, плюс
`notifyDependents`, `close()`, `scopeKey` и ожидание дочерних скоупов.

Это семейство для состояния экрана, владеющего тем, что стоит освобождать
по-человечески, — контроллерами, подписками, сокетом. `Scope` добавляет перед
состоянием контейнер зависимостей; `AsyncScope` убирает состояние и оставляет
только жизненный цикл.

```dart
final class ScreenScope extends LiteScope<ScreenScope, ScreenScopeState> {
  const ScreenScope({super.key, super.scopeKey});

  @override
  Widget? buildOnWaiting(BuildContext context) => const SizedBox.shrink();

  @override
  ScreenScopeState createState() => ScreenScopeState();

  static ScreenScopeState of(BuildContext context) =>
      LiteScope.of<ScreenScope, ScreenScopeState>(context);
}

final class ScreenScopeState
    extends LiteScopeState<ScreenScope, ScreenScopeState> {
  final controller = ScrollController();

  @override
  Future<void> disposeStateAsync() async => controller.dispose();

  @override
  Widget build(BuildContext context) =>
      ListView(controller: controller, children: const [Text('item')]);
}
```

## Состояние

`LiteScopeState` — это `State` с пятью добавками:

| член | что это |
| --- | --- |
| `initStateAsync()` | асинхронная инициализация, запускаемая, когда состояние уже есть |
| `onUnmount()` | синхронный разбор, всегда перед `disposeStateAsync()` |
| `disposeStateAsync()` | асинхронный разбор; его дожидаются, прежде чем скоуп исчезнет |
| `notifyDependents()` | перестроить подписанных потомков, а не поддерево |
| `close()` | запустить разбор, пока скоуп ещё на экране |

и с тремя собственными свойствами: `params` — виджет скоупа, так что параметры
его конструктора читаются из состояния; `isInitialized`; и `onInitialized()` —
хук, который зовут, когда инициализация полностью завершилась.

`State.widget` среди них нет и не будет: у состояния скоупа нет собственного
виджета — `params` и есть виджет скоупа, и это весь ответ. Чтение `widget`
бросает `UnsupportedError`, который так и говорит; на это натыкается миксин
к `State`, написанный для обычных виджетов.

**Миксинам тикера нужен отдельный владелец.** `SingleTickerProviderStateMixin`
и `TickerProviderStateMixin` на состоянии скоупа несовместимы с освобождением
активного `AnimationController` в `onUnmount()`: при обычном удалении Flutter
снимает потомков раньше предков, поэтому элемент состояния скоупа выполняет
проверку `dispose` миксина до того, как родительский элемент скоупа вызовет
`onUnmount()`. Результат — `was disposed with an active Ticker`, и анализатор
об этом не предупреждает.

Пусть анимацией и миксином тикера владеет обычный дочерний `State`, который
освобождает контроллер до `super.dispose()`. Например, верните
`const AnimatedMark()` из `build` состояния скоупа; такой владелец работает
и при обычном удалении, и когда `close()` снимает готовое поддерево:

```dart
class AnimatedMark extends StatefulWidget {
  const AnimatedMark({super.key});

  @override
  State<AnimatedMark> createState() => _AnimatedMarkState();
}

class _AnimatedMarkState extends State<AnimatedMark>
    with SingleTickerProviderStateMixin {
  late final AnimationController _controller;

  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this,
      duration: const Duration(seconds: 1),
    )..repeat();
  }

  @override
  void dispose() {
    _controller.dispose(); // До проверки активных тикеров в миксине.
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => FadeTransition(
        opacity: _controller,
        child: const FlutterLogo(),
      );
}
```

Обычный `initState` у `State` продолжает работать и остаётся синхронным,
а `initStateAsync` — место для `await`. `disposeStateAsync` — то, что
заставляет родительский скоуп (и `close()`) дождаться конца освобождения,
а не запустить его и забыть.

**Осторожнее всего с `dispose`.** Он принадлежит Flutter, а не скоупу,
и в порядок разбора ниже не входит: когда скоуп снимают с дерева, фреймворк
зовёт его ещё до того, как разбор скоупа вообще начнётся, а после `close()` он
не выполняется, пока дерево не снимут, — а это может случиться сильно позже или
не случиться вовсе, пока на экране закрывающий экран. Поэтому синхронная
половина разбора живёт в `onUnmount()`, которым распоряжается сам скоуп:

```dart
@override
void onUnmount() {
  _subscription.cancel();   // должно перестать доходить до скоупа немедленно
  super.onUnmount();
}

@override
Future<void> disposeStateAsync() => _connection.close();   // может занять время
```

`onUnmount()` выполняется ровно один раз и всегда до `disposeStateAsync()`,
каким бы способом скоуп ни уходил. На снятом скоупе `BuildContext` к этому
моменту уже нет, поэтому трогать там можно только то, что состояние держит
в собственных полях.

**Обе половины выполняются и после `initStateAsync()`, который бросил**, —
в том же порядке, что и после успешного, — поэтому диспозер обязан быть готов
к частично инициализированному состоянию: поле, до которого `await` не дошёл,
к моменту его вызова так и не присвоено. Упавшая инициализация — не та, которой
не было. Инициализатор, открывший соединение и бросивший строкой ниже, его
открыл, и держать его больше некому: скоуп не становится готовым, а значит
владельцу состояние не отдают вовсе, и этот хук — единственное освобождение,
какое есть. Поэтому освобождать надо здесь, а не перед каждым `throw`; чего
нельзя — так это считать, что инициализатор дошёл до конца.

## Две инициализации

Фаз две, и это не одно и то же.

`LiteScope.initScope()` на **виджете** — предварительная инициализация: обычная
`async`-функция, принимающая `ScopeInitContext`, ровно как в теме `AsyncScope`,
выполняющаяся *до* создания состояния. По умолчанию её тело пустое — готово
сразу, — поэтому большинство скоупов её не переопределяют. Переопределяйте,
когда что-то должно быть готово до `createState`; тогда придётся переопределить
и `buildOnProgress`, и `buildOnError` — их реализации по умолчанию бросают
`UnimplementedError`, исходя из того, что ненаписанная ветка прогресса — это
ошибка, а не пустой экран.

`LiteScopeState.initStateAsync()` на **состоянии** — обычная, и выполняется
она, когда состояние уже существует, — поэтому **её никто не дожидается**.
Состояние создаёт готовая ветка, так что к моменту, когда эта инициализация
может начаться, готовая ветка уже построена: первый `build` состояния идёт
раньше, чем `initStateAsync` закончится, и все пересборки, которые случатся тем
временем, — тоже.

Отсюда `isInitialized` — часть того, как пишут состояние, а не мелочь:
`late`-поле, присвоенное после `await` и прочитанное прямо из `build`, даёт
`LateInitializationError` на этом первом билде. Придержите ветку сами
и перестройте её из `onInitialized()`:

```dart
final class TitleScope extends LiteScope<TitleScope, TitleScopeState> {
  final Future<String> Function() loadTitle;

  const TitleScope({super.key, required this.loadTitle});

  @override
  Widget buildOnWaiting(BuildContext context) => const SizedBox.shrink();

  @override
  TitleScopeState createState() => TitleScopeState();
}

final class TitleScopeState
    extends LiteScopeState<TitleScope, TitleScopeState> {
  late String _title;

  @override
  Future<void> initStateAsync() async => _title = await params.loadTitle();

  @override
  void onInitialized() => setState(() {});

  @override
  Widget build(BuildContext context) {
    if (!isInitialized) {
      return const Center(child: CircularProgressIndicator.adaptive());
    }
    return Text(_title);
  }
}
```

Завершение вызывает `onInitialized()` и уведомляет подписанных потомков;
собственный `build` состояния оно не перестраивает. Вызов `setState` выше
планирует эту пересборку, чтобы экран показал загруженный заголовок.
`onInitialized()` выполняется, только пока состояние ещё на дереве.

Другой вариант — дать полю значение, с которым его можно прочитать до того, как
инициализация его заменит; вызовите `setState`, когда собственный экран
состояния должен показать изменение. А то, что обязано быть готово **прежде**
чем что-то покажут, кладут в `initScope()` на виджете: это та фаза, которая
готовую ветку действительно придерживает.

`buildOnWaiting` закрывает промежуток до того, как хоть одна из них что-то
выдала, — кадры ожидания `scopeKey` и первого события. Вернуть из него `null`
разрешено, только если переопределён `buildOnProgress`: что-то на экране быть
обязано.

Поэтому `buildOnWaiting` — единственный билдер, который `LiteScope` обязан
написать, и это наоборот к `Scope` и асинхронным семействам, где обязателен
`buildOnProgress`. Правило за обоими одно: **ровно одна ветка до готовой должна
быть написана, и это та, до которой семейство доходит наверняка.** `Scope`
всегда инициализирует контейнер, значит ветка прогресса у него есть всегда,
а ожидание можно и пропустить; `LiteScope` не инициализирует ничего своего,
значит наверняка у него есть ожидание. Поэтому перенос экрана со `Scope`
на `LiteScope` меняет один обязательный билдер на другой: `buildOnProgress`
и `buildOnError` становятся необязательными — оставляйте их, только если
переопределяете `initScope()`, — а `buildOnWaiting` становится обязательным.

`wrapState` оборачивает только готовую ветку, поэтому виджет, нужный всем
веткам, строят внутри каждого билдера.

## Доступ из поддерева

```dart
ScreenScope.of(context).controller;                    // состояние
LiteScope.select<ScreenScope, ScreenScopeState, int>(  // одно значение из него
  context,
  (state) => state.itemCount,
);
LiteScope.paramsOf<ScreenScope, ScreenScopeState>(context, listen: false);
LiteScope.selectParam<ScreenScope, ScreenScopeState, Object?>(
  context,
  (widget) => widget.scopeKey,
);
```

`of` и `maybeOf` возвращают состояние и никогда не подписывают — они для вызова
методов. `select` подписывает на одно значение, выведенное из состояния,
и вызывающего перестроят, только когда это значение изменится **и** только если
состояние позвало `notifyDependents()`. Больше за состоянием никто
не наблюдает: изменённое без этого вызова поле не дойдёт ни до кого.

`setState` — вторая половина, и её здесь никто не отбирает: состояние скоупа —
обычный `State` и сохраняет её. Половины не пересекаются, и именно это упускает
аналогия со `StatefulWidget`: `notifyDependents()` перестраивает подписчиков
и собственный `build` этого состояния не выполняет, а `setState` перестраивает
то, что возвращает собственный `build`, и до подписчиков не доходит. Полю,
которое читают обе стороны, нужны оба вызова; полю, которое читает одна, —
только её собственный.

`paramsOf` и `selectParam` делают то же самое для собственных параметров
виджета скоупа. Переоткрывать всё это именованными статиками на скоупе, как
`of` выше, — обычная практика.

## close()

```dart
await ScreenScope.of(context).close();
```

`close()` запускает разбор, пока скоуп ещё на экране, и завершается, когда
утилизация закончена. Готовое поддерево замораживается снимком, поверх
показывается `buildOnClosing`, а элемент остаётся на дереве до самого конца —
в этом и смысл: скоуп, который освобождает что-то заметное время, показывает
«закрываемся…», а не замирает на последнем кадре. Утилизация ждёт, пока снимок
заменит живое поддерево и это поддерево будет размонтировано, поэтому обычный
дочерний `State` в своём `dispose` ещё может пользоваться тем, чем владеет
состояние скоупа.

У `AsyncScope`, `AsyncDataScope` и `AsyncControllerScope` тот же `close()`, без
снимка: их ветка закрытия сразу заменяет поддерево — см. `close()` в теме
`AsyncScope`. Снимок — то, что добавляет это семейство: последний кадр остаётся
под `buildOnClosing`, а не уступает ему место.

Снимок делается по возможности, и это уточнение точное: барьер снимка ставится,
только если скоуп действительно готов и ещё на дереве, — в любом другом
состоянии освободить барьер было бы некому, и future повис бы навсегда.
Поддерево, которое никогда не рисовалось (внутри `Offstage` или в невыбранной
ветке `IndexedStack`), снять тоже нельзя; после `ScreenshotReplacer.maxRetries`
кадров `close()` идёт дальше, и готовое поддерево всё равно убирают — просто
на место картинки не встаёт ничего. Иначе нельзя: снимка ждут ровно затем,
чтобы отпустить то, что поддерево держит, а оставленное стоять поддерево держит
смонтированными и зарегистрированными свои дочерние скоупы — этот тогда
выждал бы весь `waitForChildrenTimeout` ради ребёнка, которого никто не снимал,
и освободил бы то, что ребёнок ещё читает.

Упавшая сборка закрытия разбор тоже не держит. Барьер освобождает
`ScreenshotReplacer`, которого эта сборка монтирует, — так что `wrapState` или
`buildOnClosing`, который бросил, раньше означал `close()`, не завершающийся
никогда, и четыре стадии, которые не начинались. Такой отказ теперь выходит
`ErrorWidget`-ом, в который превращается любая упавшая сборка, а разбор за ним
продолжается.

Оверлей закрытия по умолчанию берёт цвет из темы **над** скоупом, а для скоупа
в корне приложения — того, чей `wrapState` строит `MaterialApp`, — это
`ThemeData.fallback()`. Напишите там `buildOnClosing`: корневому скоупу он
и так нужен.

Второй вызов `close()` ничего не перезапускает: он присоединяется к уже идущей
утилизации, а не ставит второй барьер.

## Разбор и кто его дожидается

Порядок — тот же, что в теме `AsyncScope`, со вставленными шагами состояния:
первым выполняется `onUnmount()` состояния, предварительная инициализация
отменяется, дожидаются дочерних скоупов (`waitForChildrenTimeout`), выполняется
`disposeStateAsync()` состояния, и последним освобождается `scopeKey`, чтобы
следующий скоуп с этим ключом стартовал, только когда этот закончил.

Собственный `dispose()` состояния стоит вне этой последовательности — по одну
или по другую её сторону, смотря как скоуп ушёл: до всего, если скоуп сняли
с дерева, и после всего, если он закрылся сам. В этом и смысл `close()` —
сначала отпустить, уйти потом, — и поэтому разбор, который скоуп гарантирует,
это пара `onUnmount()`/`disposeStateAsync()`, а не `dispose()`.

`LiteScope` — такой же `AsyncScopeParent`, как любой асинхронный скоуп: скоупы
под ним встают к нему на учёт, и он дожидается их, прежде чем разбирать себя.
Попросить это ожидание из поддерева — `AsyncScopeCoordinator.waitForChildren`:
сам миксин лежит на элементе, а он здесь приватный; см. тему `AsyncScope`.
