## Оценки

**Код — 8/10.** Архитектура последовательно решает трудные задачи владения:
позднее завершение инициализации, частичный отказ, повторное закрытие, порядок
зависимостей и продолжение уборки после ошибок. Тесты содержат содержательные
проверки этих контрактов. Однако остались нарушения именно на границах
владения: раннее освобождение при `close()`, обход публичного `disposeData`,
несовпадающие ошибки одного разбора и ошибочно настроенный основной
демонстрационный сценарий закрытия.

**Документация — 8,5/10.** Теперь есть короткий вход через quickstart, таблица
семейств, подробные темы, русские зеркала и машинная проверка примеров.
Большинство обычных задач можно выполнить без чтения реализации. Недостающие
баллы — за небезопасный рецепт частичной очистки, неполное объяснение
совместимости со стандартными `State`-миксинами и обещание демонстрации,
которое её исполнение нарушает.

**Общая — 8/10.** У проекта есть самостоятельная полезная задача и серьёзная
инженерная база. Его практическую привлекательность ограничивают сложность
собственной модели жизненного цикла и пока недостаточная проверка потребления
извне. Единственный известный пользователь — автор; это не доказывает
ненужность, но оставляет непроверенными понятность API без авторских подсказок
и стоимость сопровождения чужого приложения.

## Удобство для человека

**До первого рабочего экрана теперь можно добраться разумно быстро.** Ссылка
на quickstart находится перед подробным обходом семейств. Достаточно одной
страницы инструкции и одного `lib/main.dart`: ресурс открывается, показываются
загрузка и результат, кнопка демонстрирует смену владельца. Начинать с полного
`Scope` и контейнера зависимостей не требуется.

Дальше цена освоения заметно растёт. Восемь семейств сочетаются с вариантами
`Core`, `Base`, готовыми виджетами, контекстами, состояниями и аксессорами.
README занимает 920 строк. Он годится как обзор и справочник,
но последовательное чтение всего файла не является хорошим обязательным входом.

Имена в основном предсказуемы: `.value` обозначает внешнее владение, `select` —
подписку на выбранное значение, `scopeKey` отделён от ключа виджета. Однако
результат `of` зависит от семейства: модель, контекст или состояние. Различие
`notifyDependents` и `setState`, две инициализации и особый смысл
`State.widget` приходится изучить отдельно.

Диагностика неправильного использования обычно полезна: сообщения объясняют
условие нарушения и предлагают действие; `create: null` теперь отвергается
типом. Но анализатор не закрывает поведенческие ловушки: ticker-зонд
анализируется без замечаний, а документированный `disposeData` собственного
Core-element вообще не вызывается.

Главный риск удобства здесь — возможность написать правдоподобный,
компилируемый код по публичному контракту и обнаружить расхождение только
на освобождении ресурсов.

## Удобство для агентов

### Агент, который пишет приложение на scopo

Для стандартного `AsyncDataScope` или `ScopeNotifier` публичных материалов
достаточно. Таблица выбора семейств, quickstart, темы и типизированные
аксессоры дают агенту конкретные образцы. Стенд документации существенно
снижает вероятность копирования несуществующего метода или устаревшей
сигнатуры.

При этом **103 PASS не означают 103 проверенных сценария поведения**: основная
масса проверок компиляционная. Небезопасный цикл освобождения успешно проходит
такой стенд. Агент, следуя ему буквально, воспроизведёт утечку из находки 3.

Точки расширения Core требуют большей осторожности, чем обещает их публичность.
До R1 агент не сможет надёжно вывести правильное освобождение из обязательного
`disposeData`: ему придётся читать реализацию и обнаруживать, какой
дополнительный хук реально вызывается.

### Агент, работающий в репозитории

Регламент в целом пригоден для восстановления: есть одна точка входа, текущий
handoff, отдельный backlog, карта архитектуры и исторические записи
с вердиктами. `docs/handoff.md` занимает 197 строк и прямо сообщает, что выпуск
подготовлен, но не выполнен. Существенного нового противоречия текущему коду
в этой части не установлено.

Полезны требования сохранять первоначальные находки, добавлять вердикты
на месте, проверять изменения закреплённым SDK и не включать чужие файлы
в коммит. Они делают работу следующего агента проверяемой.

Стоимость процесса высока: `AGENTS.md` — 248 строк, история — 114 файлов
примерно на 45 тысяч строк. Историю необходимо читать по ссылкам и вопросу,
а не целиком при каждом старте. Комментарии реализации тоже часто подробно
пересказывают прошлую поломку; это помогает понять защиту, но увеличивает объём
чтения.

CI хорошо переносит регламент в машину: проверяет пол, примеры, документацию
и отсутствие изменений после прогона; stable вынесен в необязательную проверку.
Новых подтверждённых дефектов CI и IDE-шаблонов не найдено. Фактическое
исполнение CI и работа живых редакторов остаются за границами проверки.

## Нужен ли проект

**Да, для узкой задачи асинхронного владения ресурсами внутри дерева
виджетов.** Смена сессии, базы, проигрывателя или соединения действительно
требует ответов на вопросы: кто владеет результатом незавершённого открытия,
когда можно запускать нового владельца, кто ждёт детей и что показывать
во время закрытия.

Сравнение с альтернативами:

| Средство | Что уже закрывает | Основание выбирать scopo |
|---|---|---|
| `provider` | Доступ через дерево, владение создаваемым объектом, подписки и селекторы. Его `Dispose<T>` возвращает `void`. | Нужен общий протокол ожидаемого асинхронного освобождения и смены владельца. Для обычного `ChangeNotifier` преимущество scopo невелико. [provider](https://pub.dev/packages/provider), [Dispose](https://pub.dev/documentation/provider/latest/provider/Dispose.html) |
| Riverpod | Асинхронные значения, зависимости провайдеров, автоматическое освобождение и отмена через `ref.onDispose`. Этот callback имеет тип `void Function()`. | Нужен явно ожидаемый разбор, связанный с деревом экранов. Из приведённого API `onDispose` такой барьер сам по себе не следует. [Automatic disposal](https://riverpod.dev/docs/concepts2/auto_dispose), [onDispose](https://pub.dev/documentation/riverpod/latest/riverpod/Ref/onDispose.html) |
| `flutter_bloc` | Модель состояния приложения, реакция интерфейса, предоставление BLoC/Cubit и их автоматическое закрытие; `RepositoryProvider` имеет callback освобождения. | Нужна координация жизненного цикла нескольких ресурсов и скоупов. scopo может владеть BLoC, сохраняя его модель состояния. [Flutter Bloc Concepts](https://bloclibrary.dev/flutter-bloc-concepts/), [RepositoryProvider](https://pub.dev/documentation/flutter_bloc/latest/flutter_bloc/RepositoryProvider-class.html) |
| `get_it` / `injectable` / `watch_it` | Скоупы, асинхронная инициализация, ожидаемый `popScope`, обратный порядок освобождения. `watch_it.pushScope` уже связывает скоуп с временем жизни виджета; `injectable` генерирует регистрации. | Это ближайшая альтернатива. Ценность scopo должна проявляться в готовом сочетании веток загрузки/ошибки, ожидания дочерних скоупов, `scopeKey` и интерфейса закрытия. [Scopes](https://flutter-it.dev/documentation/get_it/scopes), [watch_it](https://flutter-it.dev/documentation/watch_it/advanced_integration), [injectable](https://pub.dev/packages/injectable) |

Для приложения с синхронными зависимостями и обычным локальным состоянием я бы
scopo не выбирал: дополнительный жизненный цикл не окупается. Для проекта с уже
установленным Riverpod или BLoC переход всего состояния на scopo тоже
не выглядит обоснованным; полезнее оценивать его как владельца конкретных
ресурсов.

Для ресурса, которому категорически запрещено перекрытие владельцев,
стандартные трёхсекундные пределы требуют отдельного решения. README теперь
честно говорит, что после таймаута владельцы могут пересечься. Исправленное
обещание повторной находкой не считаю.

Основные препятствия принятию: цена освоения, неодинаковая надёжность готовых
фасадов и расширяемых основ, зависимость от двух пакетов одного автора
и отсутствие внешнего опыта использования. Устранять их стоит раньше добавления
девятого семейства.

- `fvm flutter test --no-pub lifecycle_probe_test.dart core_dispose_test.dart

  контроль обычного удаления дерева. Провалы те же, что в отчёте:
  `['completed', 'child.dispose']` у самого `ScreenshotReplacer`,
  `['resource.dispose', 'child.dispose']` в обоих вариантах `close()`,
  `was disposed with an active Ticker.`, `DataCore calls: []`,
  `ControllerCore calls: [controller.dispose]`,
  `leaf joined: StateError Bad state: cannot close db`
  и `group joined: ScopeDependencyException db: …`. Находки 1, 2, 5 и 6
  воспроизведены.
- `fvm dart run manual_cleanup_probe.dart` — `original error preserved: false`,
  `database closed: false`,
  `CONTRACT FAIL: cleanup skipped database and replaced init error`. Первая
  половина находки 3 воспроизведена.
- `fvm flutter test --no-pub deferred_closing_probe_test.dart`
  из `example/scopo_demo` —
  `3066 ms: timeout: its dependencies to be disposed of`,
  `close completed; finished steps: [4, 3]`, шаги 2 и 1 кончаются на 3457
  и 4592 мс. Находка 4 воспроизведена.

Механизм каждой находки сверен с кодом:

- **1.** `_ScreenshotReplacerState._capture` и `_retryOrGiveUp` вызывают
  `_reportCompleted()` сразу после `setState`, а `_runAsyncDispose` после
  `await screenshotCompleter.future` идёт в `super._performAsyncDispose()`,
  не дожидаясь кадра, который снимет ребёнка. Комментарий в `_retryOrGiveUp`
  («Before the report, so a caller … finds the subtree already on its way out»)
  показывает, что порядок «ребёнок раньше ресурса» и был намерением: находка —
  расхождение кода с его же замыслом. P1 принимаю.
- **2.** Связь `disposeScope() => disposeData(data)` есть только
  в `async_data_scope_base.dart`; у Core `disposeScope() {}`
  в `async_data_scope_core.dart` и `_controller?.performDispose()`
  в `async_controller_scope_core.dart`. Ни один тест в `test/` не заводит
  собственный Core-элемент.
- **3**, вторая половина. `initCancellationTimeout` в `async_scope_core.dart`
  читается в одном месте — в разборе, когда `_initJob` отменяют
  (`job.cancel(reason: const _ScopeDisposalCancelReason())`, затем
  `_awaitBounded`). Смонтированному скоупу, которого никто не закрывает, этот
  предел не включает никто, и абзац под рецептом в `doc/async_scope.md`
  неверен.
- **5.** `_handleDisposalError` пишет
  `_disposalFailure ??= AsyncError(error, stackTrace)` до `_handleError`,
  который и оборачивает ошибку или дописывает путь.
- **6.** `LiteScopeCoreState.dispose` — только `super.dispose()`, а `onUnmount`
  состояния вызывает элемент скоупа из своего `unmount()`
  (`scope_widget_core.dart`). Состояние живёт ниже, в элементе
  `_LiteScopeCoreWidget`, и Flutter снимает потомков раньше родителя: `dispose`
  миксина с проверкой тикера отрабатывает до `onUnmount`.

```dart
Future<List<Object>> disposalOutcomes(ScopeDependency dependency,
    Completer<void> release) async {
  final init = ScopeInitJob<void>((ctx) => dependency.init(ctx, (_) {}))..start();
  await init.value;
  Future<Object> record() => dependency.dispose((_) {}).then<Object>(
        (_) => 'success',
        onError: (Object error, StackTrace stackTrace) => error,
      );
  final first = record();
  final joined = record();
  release.complete();
  return Future.wait([first, joined]);
}

void main() {
  test('joined leaf disposal has the same named exception contract', () async {
    final release = Completer<void>();
    final dependency = ScopeDependency('db', (handle) {
      handle.dispose = () async {
        await release.future;
        throw StateError('cannot close db');
      };
    });
    final outcomes = await disposalOutcomes(dependency, release);
    print('leaf first: ${outcomes.first.runtimeType} ${outcomes.first}');
    print('leaf joined: ${outcomes.last.runtimeType} ${outcomes.last}');
    expect(outcomes.first, isA<ScopeDependencyException>());
    expect(outcomes.last, isA<ScopeDependencyException>());
  });
```

```dart
import 'dart:async';

import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:scopo/scopo.dart';
import 'package:scopo_demo/home/demos/deferred_closing/screen_scope.dart';
import 'package:scopo_demo/utils/console/console.dart';

final class RecordingObserver extends ScopeObserver {
  final events = <String>[];
  final timeouts = <TimeoutException>[];
  final completedSteps = <String>[];
  final clock = Stopwatch();

  void record(String message) {
    events.add('${clock.elapsedMilliseconds} ms: $message');
  }

  @override
  void onDisposalStepStarted(ScopeObservable target, String path) {
    record('start $path');
  }

  @override
  void onDisposalProgress(ScopeObservable target, String path) {
    completedSteps.add(path);
    record('finished $path');
  }

  @override
  void onTimeout(
    ScopeObservable target,
    String what,
    TimeoutException error,
    StackTrace stackTrace,
  ) {
    timeouts.add(error);
    record('timeout: $what: $error');
  }
}

void main() {
  testWidgets('the actual demo waits for all four releases without timing out',
      (tester) async {
    ScopeConfig.reset();
    final observer = RecordingObserver();
    ScopeConfig.observer = observer;
    console.clearAll();
    final frameworkErrors = <FlutterErrorDetails>[];
    final previousErrorHandler = FlutterError.onError;
    FlutterError.onError = frameworkErrors.add;
    var closeFinished = false;
    var completedAtClose = <String>[];
    Object? closeError;

    try {
      await tester.pumpWidget(const MaterialApp(home: ScreenScope()));
      await advance(tester, until: () => find.text('close').evaluate().isNotEmpty);
      final state = ScreenScope.of(tester.element(find.text('close')));
      final dependencies = state.dependencies;
      observer.clock.start();
      unawaited(state.close().then<void>(
        (_) {
          completedAtClose = List.of(observer.completedSteps);
          closeFinished = true;
          observer.record('close completed; finished steps: $completedAtClose');
        },
        onError: (Object error, StackTrace stackTrace) {
          closeError = error;
          closeFinished = true;
          observer.record('close failed: $error');
        },
      ));
      await advance(tester, until: () => closeFinished);
      observer.record('root still holds resources: ${dependencies.root.disposalRequired}');

      // Keep driving the actual outstanding work after close has returned.
      await advance(tester, until: () => observer.completedSteps.length == 4);
      await tester.pumpWidget(const SizedBox.shrink());
      await tester.pump();
      await tester.runAsync(
        () => Future<void>.delayed(const Duration(milliseconds: 100)),
      );
      await tester.pump();
    } finally {
      FlutterError.onError = previousErrorHandler;
      ScopeConfig.observer = null;
      ScopeConfig.reset();
    }

    print('Source: unchanged ScreenScope and ScreenDependencies from demo');
    print('Default disposal timeout: ${ScopeConfig.defaultDisposeScopeTimeout}');
    for (final event in observer.events) {
      print(event);
    }
    print('framework errors: ${frameworkErrors.map((e) => e.exception).toList()}');
    print('completed steps at close: $completedAtClose');
    print('completed steps after cleanup: ${observer.completedSteps}');
    expect(closeError, isNull);
    expect(observer.completedSteps, ['4', '3', '2', '1']);
    expect(
      observer.timeouts,
      isEmpty,
      reason: 'the documented ordinary deferred close should finish all four releases',
    );
    expect(completedAtClose, ['4', '3', '2', '1']);
    expect(frameworkErrors, isEmpty);
  });
}

Future<void> advance(

  required bool Function() until,

    await tester.runAsync(

  }
}
```
