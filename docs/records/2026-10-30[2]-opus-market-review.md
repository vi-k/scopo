## Главное

- **Ниша у scopo есть, и на 2026-10-30 никто на pub.dev не закрывает её
  целиком.** Ниша такая: ресурс со своим асинхронным жизненным циклом, которым
  владеет часть дерева виджетов. Инициализацию можно отменить, опоздавший
  результат освобождается, разбор идёт по порядку и с ожиданием, а два
  владельца одного ресурса друг за другом не перекрываются. Это подтверждено
  зондом (§2.2): из семи вариантов одной задачи все пять сценариев правильно
  прошёл только scopo со `scopeKey`.
- **Ближайший конкурент — `cobalt`/`cobalt_flutter`** (появился 2026-09-05).
  Это настоящий DI-фреймворк с виджетными скоупами, экранами загрузки и ошибки,
  упорядоченным разбором с ожиданием, подменами для тестов и инспектором.
  Отмены, прогресса, `close()` и сериализации владельцев у него нет.
- **Как DI-пакет или state management scopo не нужен:** Riverpod, get_it
  и provider закрывают эти задачи лучше и с несравнимой экосистемой. Описание
  и `topics` пакета (`dependency-injection`, `state-management`) обещают как
  раз то, в чём он слабее всего.
- **Выбрать scopo мешает не корректность, а цена входа и доверия**: 1002
  публичных элемента API, восемь семейств, три параметра типа у полного скоупа,
  11 ломающих минорных выпусков из 12 за два месяца, один автор, 3 лайка и 2
  звезды.

### 2.2. Одна задача в коде и что получается на деле

**Задача.** Экрану нужны БД и сессия. Сессия восстанавливается из БД, оба
ресурса закрываются асинхронно. Нужны загрузка, ошибка и уход с экрана посреди
инициализации.

Код ниже — из зонда `probe/` рядом с этим файлом. Конкурентов я писал так, как
учат их README, без ухищрений. Где рядом есть заметно лучший вариант, он
назван.

**scopo** (`probe/lib/scopo_screen.dart`):

```dart
AsyncDataScope<({Database db, Session session})>(
  initData: (context, ctx) async {
    ctx.progress('opening the database');
    final db = await ctx.abandonable(Database.open, discard: (db) => db.close());
    ctx.progress('restoring the session');
    final session = await ctx.abandonable(
      () => Session.restore(db),
      discard: (session) => session.close(),
    );
    return (db: db, session: session);
  },
  disposeData: (account) async {
    await account.session.close();
    await account.db.close();
  },
  progressBuilder: (context, progress) => Text('loading: $progress'),
  errorBuilder: (context, error, stackTrace, progress) => Text('error: $error'),
  builder: (context, account) => Text('ready: ${account.session.user}'),
)
```

**Riverpod** (`probe/lib/riverpod_screen.dart`). Охрана `ref.mounted`
обязательна: без неё Riverpod 3 бросает `UnmountedRefException`
на `ref.onDispose` после ухода, и БД остаётся открытой.

```dart
final dbProvider = FutureProvider.autoDispose<Database>((ref) async {
  final db = await Database.open();
  if (!ref.mounted) { unawaited(db.close()); throw StateError('left'); }
  ref.onDispose(() => unawaited(db.close()));   // синхронный колбэк
  return db;
});
final sessionProvider = FutureProvider.autoDispose<Session>((ref) async {
  final db = await ref.watch(dbProvider.future);
  final session = await Session.restore(db);
  if (!ref.mounted) { unawaited(session.close()); throw StateError('left'); }
  ref.onDispose(() => unawaited(session.close()));
  return session;
});
// в ConsumerWidget: switch (ref.watch(sessionProvider)) { AsyncData … AsyncError … _ => loading }
```

**get_it + watch_it** (`probe/lib/watch_it_screen.dart`):

```dart
pushScope(init: (getIt) => getIt
  ..registerSingletonAsync<Database>(Database.open, dispose: (db) => db.close())
  ..registerSingletonAsync<Session>(
    () => Session.restore(getIt<Database>()),
    dependsOn: [Database],
    dispose: (session) => session.close(),

final ready = allReady(onError: …);
```

**Что показал зонд.** `probe/test/lifecycle_test.dart` — виджет-тест
на фейковом времени: открытие и восстановление идут по 100 мс, закрытие — 50
мс. Ресурсы пишут журнал, полный вывод — в `probe/run2.txt` и `probe/run3.txt`.
Тулчейн — глобальный Flutter 3.47.0 / Dart 3.13.0, scopo взят с pub.dev
(0.21.0), а не из рабочей копии.

| сценарий | scopo | scopo + `scopeKey` | cobalt_flutter | riverpod (с `ref.mounted`) | riverpod (как в доках) | get_it + watch_it | depend |
| --- | --- | --- | --- | --- | --- | --- | --- |
| готов → уход: порядок закрытия | сессия, затем БД, последовательно | — | сессия, затем БД | закрытие БД начинается раньше, чем закрылась сессия | так же | сессия, затем БД | так же, как riverpod |
| уход во время открытия БД | БД закрыта по приходу, сессия **не начата** | — | init доведён до конца: сессия восстановлена для ушедшего экрана, потом всё закрыто | БД закрыта | **БД не закрыта** | **`StateError` в зоне, БД не закрыта** | **БД и сессия не закрыты** |
| сессия не восстановилась | ошибка на экране, БД закрыта | — | ошибка, БД закрыта | ошибка, БД закрыта | ошибка, БД закрыта | ошибка, БД закрыта | ошибка, **БД не закрыта** |
| родитель перестроил экран | один комплект | — | один | один | один | один | **второй комплект открыт, первый утёк** |
| мгновенное переоткрытие (новый элемент) | новая БД открывается до закрытия старой | **старая закрыта целиком, потом открыта новая** | перекрытие, как у scopo | новый экран получил тот же экземпляр (провайдер глобален) | так же | перекрытие | перекрытие |

Как это читать:

- **Всё правильно в каждом сценарии — только у scopo со `scopeKey`.** Без ключа
  scopo перекрывает владельцев так же, как cobalt и get_it. README говорит это
  прямо (`README.md:30–32`, `:696–702`): ключ не включён по умолчанию,
  а ожидание ограничено 3 с.
- **cobalt корректен, но не экономен:** уход посреди старта не отменяет работу,
  она доводится до конца и выбрасывается. Для БД и сессии это лишние 100–200
  мс. Для загрузки или подключения к устройству — заметно больше.
- **Riverpod** делает задачу и корректно, если знать про `ref.mounted`,
  но порядка закрытия не держит: колбэки синхронны, и ждать некому. Порядок
  внутри одного провайдера можно получить общим `onDispose(() async {…})`,
  но и тогда его никто не ждёт. Переоткрытие в Riverpod — вообще другая модель:
  экземпляр принадлежит провайдеру, а не экрану.
- **get_it + watch_it** с идиоматичным кодом теряет опоздавшую БД и бросает
  ошибку в зону: скоуп уже снят, а зависимая фабрика ещё идёт.
- **depend** демонстрирует, чего стоит наивная реализация: повторная
  инициализация на каждую пересборку и утечки на всех нештатных путях.

Ограничения зонда: один сценарий на фейковом времени, конкурентов писал я. Пять
строк журнала на сценарий — не доказательство корректности scopo вообще. Это
доказательство, что его обещания из README в этих пяти сценариях выполняются,
а у соседей — нет.

### 2.3. Где scopo сильнее и где слабее

**Сильнее всех на рынке** (по найденному):

1. **Отмена инициализации с освобождением опоздавшего.** Это структурированная
   конкурентность (ядро `async_job`) поверх дерева виджетов. Ни cobalt,
   ни yx_scope, ни get_it её не дают: все трое ждут завершения. Riverpod даёт
   отмену только по соглашению.
2. **`scopeKey`.** Сериализацию владельцев одного ресурса в дереве не делает
   больше никто. Ближе всех yx_scope: его `init` ждёт `dispose` прошлого
   состояния, но только внутри одного holder'а вне дерева.
3. **`close()` с экраном закрытия** и `Future`, который завершается вместе
   с разбором (`README.md:749–785`). Аналогов не нашёл.
4. **Прогресс как часть контракта** (`ctx.progress`, путь шага
   в `ScopeAutoDependenciesProgress`) и наблюдатель с маршрутом ошибки
   (`ScopeErrorRoute`, `README.md:828–866`). Это глубже логов get_it
   и `ProviderObserver`. С инспектором cobalt — сопоставимо по смыслу,
   но слабее по инструментам (UI инспектора у scopo нет).
5. **Тесты и честность документации.** 825 тестов (`docs/handoff.md:181`),
   отслеживание утечек на всей сьюте, блоки `doc/` проверяются стендом. README
   сам говорит, когда scopo не нужен (`README.md:53–55`), и прямо описывает
   компромиссы таймаутов.

**Слабее:**

1. **Это не DI в рыночном смысле.** Нет регистрации по интерфейсу, поиск идёт
   по точному типу виджета (`base.dart:244`). Нет графа с ленивыми синглтонами,
   нет подмен для тестов. «Контейнер» — класс, который пишут руками или через
   `ScopeAutoDependencies`. Слова `dependency-injection` в `topics`
   и «dependency injection» в описании пакета (`pubspec.yaml:2–3`, `:9–13`)
   приводят того, кто ищет get_it или cobalt, и он уходит разочарованным.
2. **Порог входа.** 1002 публичных элемента (страница score), восемь семейств
   (`README.md:102–117`), `Scope<App, AppDependencies, AppState>` с тремя
   параметрами типа, которые нужно повторять в каждом статике. Ради этого
   в пакете есть аксессоры и редакторные шаблоны (`README.md:608–692`): само их
   существование говорит о цене. У cobalt пример на 25 строк умещается в один
   экран README, у scopo минимальный полный `Scope` занимает
   `README.md:408–607`.
3. **Нет повтора после ошибки и нет подмены зависимостей в тестах.** Обе вещи
   есть у cobalt и Riverpod. У scopo повтор делается сменой `Key`, подмена —
   отдельным тестовым скоупом.
4. **Стабильность API.** Начиная с 0.10.0 (2026-08-23) вышло 12 минорных версий
   до 0.21.0 (2026-10-28). Ломающие изменения есть в 11 из них, всего 35
   пометок `**Breaking`. `CHANGELOG.md` — 2736 строк. Выпуски 0.20.0 и 0.21.0
   сломали API только из-за ядра (`CHANGELOG.md:1–22`). Для стороннего
   пользователя это означает переписывать код каждые 5–6 дней.
5. **Две неизвестные зависимости вместо одной.** `async_job` 0.6.0 — 0 лайков,
   444 загрузки. Он реэкспортируется (`lib/scopo.dart:7–24`) и прибит
   к `^0.6.0`.
6. **Вес кода и документов.** В `lib/` 13 338 строк, из них кода около 6 500,
   dartdoc — 3 688, внутренних комментариев — 1 647. `async_scope_core.dart` —
   1722 строки, из них около 700 — комментарии. README — 1006 строк,
   `doc/debug.md` — 839. Документация исчерпывающая, но это справочник
   по граничным случаям, а не путь от «зачем» к «как». Это мнение.
7. **Экосистема и автор.** Один автор, 3 лайка, 2 звезды, 0 открытых issue
   (то есть нет и обратной связи). Сторонних статей, адаптеров и примеров
   не нашёл.

- **disco — 5,6 / 5,3 и flutter_lean_di — 5,4 / 5,1.** Удобный синхронный
  скоупный DI с подменами и хорошей эргономикой. Асинхронного цикла нет совсем,
  он вынесен наружу. У lean_di за спиной компания (LeanCode), но пакету три
  недели.
- **depend — 3,6 / 3,5.** Задача та же, но реализация ломается на трёх
  сценариях из пяти (§2.2): `create()` в `build`, `dispose` синхронный
  и разбирает только пришедшее.

## 4. Вывод: нужен ли scopo

**Дублирует ли он существующее?** Как DI-контейнер и как state management — да,
и проигрывает: get_it, Riverpod и provider делают это проще, с подменами,
поиском по интерфейсу и огромной экосистемой. Три семейства из восьми
(`ScopeWidgetBase`, `ScopeModel`, `ScopeNotifier`) и отчасти `AsyncScope`
повторяют `provider` с другим синтаксисом.

**Есть ли ниша, которую не закрывает никто?** Да, и она узкая: **корректный
асинхронный жизненный цикл ресурса, которым владеет поддерево.** Это отмена
незаконченного старта, освобождение опоздавшего значения, упорядоченный
и ожидаемый разбор после детей, сериализация владельцев и закрытие на месте.
Среди 91 найденного кандидата всё это вместе не делает никто. Ближе всех
cobalt, но без отмены, прогресса, `close()` и `scopeKey`. Следом yx_scope — без
владения виджетом и без отмены.

**Кому он нужен.** Приложениям, где ресурс эксклюзивен или дорог, а экран живёт
недолго: камера, BLE и другое железо, аудио- или видеоплеер, файлы БД
с блокировкой, сокет или сессия на раздел, тяжёлая офлайн-инициализация
по разделам, киоски и встроенные системы. И командам, которые готовы платить
сложностью за детерминированный разбор. Сегодня это одна команда — сам автор.

**Кому не нужен.** CRUD-приложениям, где всё синхронно или терпит `unawaited`.
Командам на Riverpod или Bloc + get_it: утечка опоздавшего ресурса при быстром
«назад» там случается редко и чинится локально. Тем, кому нужен DI
с интерфейсами, кодогенерацией и подменами. Новичкам.

**Что мешает его выбрать**, по убыванию веса (это мнение):

1. **Нет социального доказательства**: 3 лайка, 2 звезды, один автор,
   ни статей, ни упоминаний. Рядом то же самое у cobalt, а Riverpod в 1000 раз
   заметнее.
2. **Нестабильный API**: 11 ломающих выпусков из 12 за два месяца, версия 0.x,
   а ядро `async_job` тоже 0.x того же автора.
3. **Порог входа**: 1002 элемента API, восемь семейств, три параметра типа.
   Шаблоны редактора нужны, чтобы с этим жить.
4. **Неверная витрина**: `topics` и описание продают DI и state management,
   то есть то, в чём он слабее. Своё сильное — отмену, `scopeKey` и `close()` —
   пакет прячет в середину README.
5. **Прямой соперник за ту же крошечную аудиторию**: cobalt появился 2026-09-05
   с похожей подачей («Widgets own scopes, startup shows loading and error
   screens»), лучшей DI-историей и инспектором.

**Итог без смягчений.** Как «ещё один DI / state management» scopo не нужен:
его не выберут и не должны выбирать. Как слой корректного жизненного цикла
ресурсов в дереве он уникален на pub.dev — насколько это видно из моего поиска
на 2026-10-30. Но уникальность в нише, которую большинство не замечает,
не превращается в пользователей сама: пока витрина обещает DI, а API меняется
раз в неделю, внешний пользователь у пакета не появится.

По приоритету. Цена — в рабочих днях одного разработчика, оценка грубая;
отдача — моё мнение.

1. **Перепозиционировать пакет.** Цена — 1–2 дня, отдача высокая. Описание
   `pubspec.yaml`: вместо «managing scopes and dependency injection» — что-то
   вроде «async resource lifecycle in the widget tree: cancellable
   initialization, ordered awaited teardown, serialized owners». `topics`:
   убрать `state-management`, оставить `dependency-injection` вторым, добавить
   `lifecycle`/`async`. README начать с таблицы вида §2.2 — что происходит,
   когда пользователь уходит с экрана во время загрузки, в scopo и у соседей.
   Это единственный рычаг узнаваемости, который почти ничего не стоит.
2. **Заморозить API и выйти в 1.0.** Цена — дисциплина плюс 2–3 дня на ревизию
   имён, отдача высокая для доверия. Отвязать выпуски scopo от подъёмов пола
   ядра. 0.20.0 и 0.21.0 сломали scopo без изменения его API: это повод сузить
   реэкспорт `async_job` (`lib/scopo.dart:7–24`) до того, что действительно
   нужно в сигнатурах scopo. Договориться о ритме, например не чаще одного
   ломающего выпуска в квартал.
3. **Сузить первую встречу.** Цена — 3–5 дней, ломающая правка; раз
   пользователь пока один, она дешёвая. Отдача средняя или высокая. Вперёд
   выставить два входа — `AsyncDataScope` и `Scope` + `ScopeAutoDependencies` —
   и `AsyncControllerScope` как третий. `ScopeWidgetBase`, `ScopeModel`,
   `ScopeNotifier` и утилиты `listenable` повторяют provider: вынести их
   в отдельную библиотеку (`package:scopo/structural.dart`) или вообще убрать
   из витрины. Цель — чтобы `package:scopo/scopo.dart` был заметно меньше 1002
   элементов.
4. **Закрыть два очевидных пробела.** Цена — 2–4 дня, отдача средняя. (а)
   Повтор из ветки ошибки: `retry()` в аргументах `errorBuilder` или
   на контексте скоупа — у cobalt и Riverpod он есть, у scopo его делают сменой
   `Key`. (б) Подмена зависимостей в виджет-тестах: например, параметр, который
   заменяет `initDependencies` тестовым телом, или виджет-обёртка с подменами
   по типу скоупа. Поиск по интерфейсу не добавлять: это шаг к DI-контейнеру,
   которым пакет быть не должен.
5. **Дружить с большими, а не воевать.** Цена — 3–5 дней, отдача средняя.
   Реалистичный путь к пользователям: scopo как владелец жизненного цикла для
   того, что уже есть у команды. Это рецепт-тема и пример: скоуп, который
   поднимает `ProviderContainer` или get_it-скоуп и снимает его с ожиданием;
   `AsyncControllerScope` вокруг `Bloc`; `scopeKey` для камеры поверх Riverpod.
   Тогда scopo — не «вместо Riverpod», а «то, чего Riverpod не делает».
6. **Переписать README как путь, а не справочник.** Цена — 2–3 дня, отдача
   средняя. Сейчас в нём 1006 строк. Нужно около 300: зачем, две минуты
   до первого экрана, таблица семейств, ссылки на темы. Граничные случаи
   (`README.md:694–867` — `scopeKey`, закрытие на месте, наблюдатель и маршруты
   ошибок) уже есть в `doc/`, в README им не место. Отдельно — длинные
   комментарии-эссе в `lib/` (около 1 650 строк `//`): история решений просится
   в `docs/records/`, а у кода останется «что и почему» в паре строк. Это
   мнение, но для будущего контрибьютора это барьер.
7. **Показать живой случай.** Цена — 3–5 дней, отдача неопределённая.
   Пример-приложение, где выгода видна глазами: камера или плеер, быстрое
   «вперёд-назад», журнал наблюдателя. Плюс одна статья (dev.to или Habr)
   с тем же зондом, что в §2.2. Без внешнего текста пакет некому найти.

**Чего не делать:**

- не добавлять генератор, граф и ленивые синглтоны ради соревнования с cobalt,
  get_it и injectable — это чужая игра, и там она уже выиграна;
- не добавлять кеширование и реактивные запросы ради соревнования с Riverpod;
- не расширять число семейств: просьба из `docs/backlog.md` о семействе «стрим
  кормит модель после готовности» — ровно такой шаг.

**Сужать или расширять охват?** Сужать. Ядро ценности — `AsyncScopeCore`
с отменой, ожиданием детей, `scopeKey` и `close()`. Всё, что повторяет
provider, размывает это ядро и раздувает API.
