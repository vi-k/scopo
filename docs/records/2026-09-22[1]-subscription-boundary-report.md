# Граница «подписка берётся только из сборки»: перерисована по зависимому

> **Состояние на 2026-09-22:** сделано и смержено, `01642bd`. **Что это:**
> разбор двух дефектов ассерта в `ScopeContext._find` — отвергнутого
> item-билдера и непойманного `didChangeDependencies` под layout-колбэком — с
> замерами, отвергнутым вариантом и остатком. **Связанные записи:**
> `2026-08-16[12]-project-review.md` (находка P2-15, откуда ассерт),
> `2026-08-20[1]-project-review.md` (находка про layout-колбэк, где цена была
> названа), `2026-09-22[2]-assert-error-form-report.md` (форма отказа, решённая
> сразу после).

## Повод

Владелец принёс замечание от соседа: «`didChangeDependencies` подписывается на
параметры скоупа вне build — scopo это запрещает прямым ассертом». Замечание
верное и по адресу: Flutter в дартдоке `State.didChangeDependencies`
(`framework.dart:1475-1477` у 3.27.0) прямо обещает, что звать оттуда
`dependOnInheritedWidgetOfExactType` безопасно, и для голого `InheritedWidget`
это правда — регистрация там не по-сборочная, `_dependencies` чистится только в
`activate`/`deactivate` (`framework.dart:4614`, `:4645`). У scopo подписка
несёт значение аспекта, которое надо сбрасывать каждую сборку, и границей
сброса взят кадр (`scope_widget_core.dart:8-51`). Время жизни аспекта Flutter
не документирует нигде: `InheritedModel` копит аспекты в `HashSet` и не чистит
их никогда (`inherited_model.dart:220-232`).

Проверка этого объяснения началась с единственного известного изъяна — дыры,
названной ценой в `2026-08-20[1]-project-review.md`: `didChangeDependencies`
виджета, стоящего под layout-колбэком, ассерт не ловил. Зондом нашлась обратная
ошибка, которая важнее.

## Дефект 1: ассерт отвергал item-билдер ленивого списка

`ListView.builder` строит элементы из двух разных мест. На монтировании — из
`performLayout`, то есть под `RenderObject.debugActiveLayout`. На любом кадре,
где родитель отдал новый делегат, — из собственного `performRebuild`
сливер-элемента, **в фазе сборки**, когда layout ещё не начинался.
`debugDoingBuild` не поднят ни там ни там: `RenderObjectElement` поднимает его
только вокруг `updateRenderObject`. Прежнее условие (`debugDoingBuild ||
debugActiveLayout != null`) пропускало первый случай и отвергало второй.

Зонд на настоящем API: `select` из `itemBuilder` проходит на монтировании и
падает ассертом `base.dart:143` на первой же пересборке от родителя. То есть
обычный код потребителя ломался в debug, а в release работал — ровно тот разрыв
debug и release, ради которого волна 18 расширяла это условие в прошлый раз.

## Дефект 2: под layout-колбэком не ловился `didChangeDependencies`

`debugActiveLayout` поднят на всё, что строится внутри layout-колбэка, а не
только на сам билдер, поэтому разрешение «идёт layout-колбэк» разрешало заодно
и ошибку. Это было названо ценой прямо в вердикте находки и в теме `base`.

## Замер: двенадцать точек одного кадра

Прежний замер (`2026-08-20[1]`, четыре точки, три флага) показывал, что
четвёртая строка неотличима от третьей. Добавлены два столбца — `context is
RenderObjectElement` и `Element.dirty`:

```
                                       build owner layout roe dirty
didChangeDependencies                    n     y     n     n    y
build                                    y     y     n     n    y
LayoutBuilder builder                    n     y     y     y    n
LayoutBuilder, outer context             n     y     y     n    n
ListView.builder itemBuilder             n     y     y     y    n
didChangeDependencies under layout       n     y     y     n    y
--- пересборка от родителя ---
didUpdateWidget                          n     y     n     n    y
build                                    y     y     n     n    n
ListView.builder itemBuilder             n     y     n     y    n
LayoutBuilder builder                    n     y     y     y    n
LayoutBuilder, outer context             n     y     y     n    n
--- вне кадра ---
колбэк между кадрами                     n     n     n     n    n
```

Читается так: **`dirty` делит таблицу ровно по нужной линии.** Элемент,
которого фреймворк пересобирает прямо сейчас, остаётся грязным до конца своей
`performRebuild`, а `didChangeDependencies` зовут до неё
(`StatefulElement.performRebuild` зовёт хук перед `super`). Элемент, который
бежит билдер для кого-то другого, к этому моменту уже вычищен:
`SliverMultiBoxAdaptorElement.performRebuild` первой же строкой зовёт
`super.performRebuild()`, который снимает флаг, и только потом строит детей
(`sliver.dart:867-868`), а `_LayoutBuilderElement.markNeedsBuild` вообще
не помечает себя грязным («the element is clean as soon as this method
returns», `layout_builder.dart:160-167`).

## Отвергнутый вариант: сверка render-объекта

Первым кандидатом было «контекст — это `RenderObjectElement`, чей
`renderObject` и есть `debugActiveLayout`». Замер его убил: у
`ListView.builder` на втором кадре `ownRenderObject=false` — элементы строятся
из фазы сборки, где `debugActiveLayout` пуст вовсе. Условие отсекло бы обычный
`itemBuilder`, то есть повторило бы дефект 1 в новой форме.

## Принятое условие

`_debugRegistrationBelongsToABuild` в `base.dart`, четыре ветки подряд:
собственная сборка зависимого (`debugDoingBuild`); ничего не строится вовсе
(`BuildOwner.debugBuilding` — отказ); контекст `RenderObjectElement` (билдер
ленивого элемента: у него нет хука, откуда можно подписаться по ошибке,
пользовательский код с этим контекстом — только билдер); layout-колбэк,
читающий скоуп через контекст виджета выше (`debugActiveLayout != null &&
!dirty`).

## Нагруженность

Четыре мутации, каждая по своей ветке. Снятие ветки `RenderObjectElement` валит
тест про item-билдер; снятие `!dirty` валит тест про `didChangeDependencies`
под layout-колбэком. Две другие ветки на первом прогоне **пережили мутацию на
всей сьюте** — то есть сьюта их не достигала; закрыты двумя новыми тестами
(подписка через контекст выше и подписка между кадрами со спрятанным
контекстом). После них красна каждая из четырёх. Тестов 537 → 541.

## Что осталось непойманным

`didUpdateWidget` виджета, который сам стоит под layout-колбэком: замерено —
`dirty=n`, значит проходит как билдер. Вне layout-колбэка тот же
`didUpdateWidget` отвергается. Прежняя дыра была шире (под layout-колбэком
проходило всё), так что остаток — сужение, а не новая потеря.

## Почему это не может быть громким в release

Владелец спросил, не сделать ли ошибку громкой — через `FlutterError`.
Проверено по исходникам закреплённого SDK: нельзя, и не из соображений шума.
Все три признака, на которых стоит проверка, Flutter выставляет **внутри
`assert(() {…}())`**: `_debugDoingBuild` (`framework.dart:5627`, `:6597`,
`:6643`), `_debugBuilding` (`framework.dart:3005`), `_debugActiveLayout`
(`object.dart:2455-2458`). В release они отвечают «нигде ничего не строится»
всем подряд, так что проверка в release пометила бы ошибкой каждую законную
подписку. Единственный вход, живущий в release, — `Element.dirty`
(`framework.dart:5144`), и одного его мало: он не отличает сборку от колбэка
таймера. Это тот же вывод, что записан в handoff про `isBuilding` (P2-7):
не-ассертного признака чужой сборки у фреймворка нет вовсе.

Отдельный вопрос — форма отказа **в debug**: ассерт бросает из
`didChangeDependencies`, рвёт кадр и оставляет поддерево неразмонтированным
(оттуда `experimentalLeakTesting: unmountableTree` у тестов на отказ). Замена
броска на `FlutterError.reportError` внутри `assert(() {…}())` дала бы диагноз,
не ломая дерева, но оставила бы приложение работать с подпиской, которая всё
равно умрёт. Не сделано: решение о форме отказа — за владельцем.

## Поправка к записи в handoff

В «Граблях» стояло: «`Element.dirty` во время `build()` всегда `true`». Это
неверно, и замер выше это показывает: при пересборке **от родителя** `_dirty` в
`build()` равен `false` — его поднимает только `markNeedsBuild`, а родительская
пересборка идёт через `update()`. Утверждение верно лишь для пересборки от
`setState` или от изменения зависимостей. Строка поправлена.
