# Регистрации в разных кадрах: две формы, которые тихо устаревали

> **Состояние на 2026-09-22:** сделано и смержено. **Что это:** замер двух
> форм подписки, которые пакет разрешал и которые молча устаревали, и сужение
> правила `_debugRegistrationBelongsToABuild` до «своя `build` либо билдер,
> который перезапускается целиком». **Связанные записи:**
> `2026-09-22[1]-subscription-boundary-report.md` (правило, которое здесь
> сужено; его разрешение для item-билдера отменено),
> `2026-09-22[2]-assert-error-form-report.md` (форма отказа, в которой написан
> новый текст), `2026-08-16[12]-project-review.md` (находка P2-15, откуда
> ассерт вообще взялся).

## Повод

Владелец спросил, прочитав в `doc/base.md` раздел про provider: «что
по ленивому списку? нам не надо сделать как у provider?» — provider отвергает
`select` из item-билдера, а мы его разрешали, и в тексте раздела было сказано,
что разрешаем сознательно, потому что это «обычный рабочий код». Вопрос был
про цену пересборки. Замер показал, что дело не в цене.

## Замер 1: ленивый список теряет подписки при прокрутке

`ListView.builder`, `itemExtent: 100`, `cacheExtent: 0`, окно 300; в билдере
`select` значения своей ячейки, у каждой ячейки своё значение:

```
built on mount: [0, 1, 2]
no scroll, bump(0): item 0 shows 1 -> true,  rebuilt: [0, 1, 2]
after a 50px scroll, built: [3]
after scroll, bump(0): item 0 shows 2 -> false, stale at 1 -> true, rebuilt: []
then bump(3): item 3 shows 1 -> true, rebuilt: [0, 1, 2, 3]
```

До прокрутки всё работает. Прокрутка создаёт ячейку 3 **в следующем кадре** —
это новый проход, набор сбрасывается, и в нём остаётся только её селектор.
После этого изменение значения ячейки 0 не будит никого: она показывает старое,
пока случайно не сработает чей-нибудь чужой селектор и не перестроит список
целиком (последняя строка — именно это).

## Замер 2: layout-колбэк через контекст виджета над ним

Ту же болезнь имеет форма, которую `doc/base.md` прямо благословлял: колбэк
`LayoutBuilder`, читающий скоуп через контекст виджета вокруг. Виджет выбирает
`a` в своей `build` и `b` из колбэка по внешнему контексту; дальше идёт
перелэйаут без пересборки — родитель поменял размер, сам виджет не строился:

```
callback #3 before select: pairs=2 pass=220970948
callback #3 after  select: pairs=1 pass=938474932
bumpA after the relayout: builds=2  a seen=1  a actual=2
```

`a` из набора исчез, зависимый не будится, показывает старое.

## Причина одна

Граница прохода взята по кадру (`_buildPass` в `scope_widget_core.dart`),
а регистрации **одного** зависимого законно приходят в разных кадрах: ленивый
список строит ячейки порциями, layout-колбэк бежит без пересборки владельца.
Поздняя регистрация выглядит как новая сборка и стирает всё, что тот же
зависимый зарегистрировал раньше.

Чинить саму границу нечем — это закрытый вопрос P2-15: хука «этот зависимый
сейчас начнёт строиться» у Flutter нет, а накопление без сброса — болезнь
`InheritedModel`, разобранная в `doc/base.md`. Значит, чинится правило: брать
подписку можно только там, где **всё** запрошенное зависимым запрашивается
заново разом.

## Что можно оставить: замер допустимых форм

Свойство «перезапускается целиком» есть не только у `LayoutBuilder`. Проверено
на живых виджетах:

- **`Builder` вокруг ячейки** (совет, который теперь стоит в тексте ошибки) —
  у ячейки собственный элемент, собственная сборка, собственный набор:

  ```
  BUILDER built on mount: [0, 1, 2]
  BUILDER after a 50px scroll, built: [3]
  BUILDER after scroll, bump(0): item 0 shows 1 -> true, rebuilt: [0]
  BUILDER then bump(3): item 3 shows 1 -> true, rebuilt: [3]
  ```

  То есть совет не только снимает устаревание, но и делает подписку точечной:
  будится одна ячейка вместо всего списка — ровно то, ради чего совет и даёт
  provider;
- **делегат `SliverPersistentHeader`** — строит одного ребёнка заново на каждое
  изменение shrink-смещения, и это единственный пользовательский код с его
  контекстом:

  ```
  HEADER build #1: widget=_SliverPinnedPersistentHeader
      doingBuild=false activeLayout=true isPersistentHeader=true
      renderObject=_RenderSliverPinnedPersistentHeaderForWidgets
  HEADER on mount: builds=1 seen=0 exception=null
  HEADER after bump: builds=2 seen=1
  HEADER after a 30px scroll: builds=3 seen=1
  HEADER after scroll then bump: builds=4 seen=2 actual=2
  ```

  Подписка переживает и перелэйаут в отдельном кадре. Виджет и элемент у него
  приватные, но render-объект публичен — `RenderSliverPersistentHeader`,
  по нему и опознаётся.

## Принятое правило

```dart
if (context.debugDoingBuild) return true;            // своя сборка
if (RenderObject.debugActiveLayout == null) return false;
if (context.widget is ConstrainedLayoutBuilder) return true;
return context is RenderObjectElement &&
    context.renderObject is RenderSliverPersistentHeader;
```

`ConstrainedLayoutBuilder` — общий предок `LayoutBuilder`
и `SliverLayoutBuilder`; `OrientationBuilder` отдаёт в свой билдер контекст
первого, поэтому проходит вместе с ним. **Шире, чем у provider:** тот
проверяет `widget is LayoutBuilder` по имени и потому отвергает законный
`SliverLayoutBuilder`.

Пропала ветка `context is RenderObjectElement` (она и разрешала item-билдер)
и пропало чтение `Element.dirty` вместе с проверкой
`BuildOwner.debugBuilding`: правило больше не спрашивает, какая идёт фаза,
оно спрашивает, какой это билдер. В `scope.dart` добавлен импорт
`package:flutter/rendering.dart` — `RenderSliverPersistentHeader` через
`material.dart` не реэкспортируется.

## Тексты отказа

Заголовок прежний — «A scope can only be subscribed to from a build.»;
объяснение переписано под настоящую причину (регистрации разных кадров
не складываются, поздние заменяют ранние), и добавлены два совета: контекст
самого билдера вместо внешнего и `Builder` вокруг ячейки списка. Оба совета
проверены тестами, а не только написаны.

## Нагруженность

Четыре мутации, каждая по своей ветке, на всей сьюте:

| ветка | падает |
| --- | --- |
| своя `build` | 56 тестов |
| «вне layout — отказ» | подписка между кадрами |
| `ConstrainedLayoutBuilder` | layout-колбэк и sliver-layout-колбэк |
| постоянный заголовок | делегат постоянного заголовка |

Ни одна не пережила. Тестов 541 → 545: два разрешавших теста переписаны
в отвергающие, добавлены пять (sliver-layout-колбэк, делегат заголовка,
отказ item-билдеру, `Builder` внутри ячейки, `didUpdateWidget` под
layout-колбэком), тест «между кадрами» переведён на контекст `LayoutBuilder` —
иначе ветка «вне layout — отказ» мутацию переживала.

## Что это пересматривает

- **Разрешение из `01642bd` отменено.** Диагноз той работы («черта
  по зависимому, а не по фазе») остаётся верным, а вывод «билдер, который
  фреймворк крутит за элемент, — тоже сборка» был выдан форме, которая на деле
  не работает. Тогда проверялось, что подписка берётся и переживает пересборку
  от родителя; что она переживает **прокрутку**, не проверялось;
- **абзац `doc/base.md` про «обычный рабочий код, отвергать который
  debug-сборке незачем» снят** — он был неправдой; раздел про provider теперь
  говорит, что мы отвергаем item-билдер тоже и по более твёрдой причине,
  чем цена пересборки;
- **остаток `01642bd` закрыт**: `didUpdateWidget` под layout-колбэком теперь
  отвергается — он не своя `build` и не билдер из списка выше;
- в `CHANGELOG.md` два пункта **Fix** прежних волн заменены одним: 0.15.2
  не выпущена, и читатель никогда не видел промежуточного поведения, так что
  описывать надо разницу с 0.15.1, а не ход работы.

## Чего это не закрывает

Подписка через контекст `LayoutBuilder`, украденный наружу и использованный
во время чужого layout, правилом пройдёт. Форма надуманная, у provider ровно
та же дыра, специально не проверялась.
