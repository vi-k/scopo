## Оценки

**Код — 9/10.** Основные пути владения ресурсами хорошо проработаны: позднее
завершение инициализации, отмена, частичное освобождение, ожидание детей,
повторное закрытие и ошибки пользовательских хуков имеют содержательные
проверки. В штатных сценариях нового воспроизводимого нарушения корректности
ядра не обнаружено. Недостающий балл — два дефекта восстановления после
неправильного вызова API и два дефекта инструментов, которым доверяют
доказательство качества проекта.

**Документация — 8,5/10.** README, quickstart, тематические страницы,
исполняемые примеры и русские зеркала дают достаточно материала для
самостоятельного приложения. Однако проверка блоков кода пропускает неверные
инструкции между блоками: синхронный возврат вместо `Future`, слишком широкое
обещание ошибок `close()`, неверное описание результата `Scope.of`. Зелёный
dartdoc также пропускает сломанную ссылку на нужный обход ограничения ticker.

**Общая — 8,5/10.** У проекта есть определённая практическая задача и серьёзная
инженерная база. Независимый агентский эксперимент уже полезнее очередного
внутреннего примера, но он ограничен учебной задачей и предшествует нынешнему
использованию `close()` в эталонах. Единственный известный пользователь
остаётся автором; пригодность для разных приложений пока доказана слабее, чем
работоспособность механизмов.

## Удобство для человека

До первого рабочего экрана теперь есть короткий маршрут: установка,
`example/quickstart`, один `AsyncDataScope`, создание и освобождение значения,
ветки загрузки и готовности. Изучать все восемь семейств и устройство элементов
для этого не требуется. Это существенное достоинство нынешнего входа.

Сложность появляется при первом экране с настоящим ресурсом. Нужно различать
`Widget.key` и `scopeKey`, понимать отмену ожидания и освобождение позднего
результата, знать о трёхсекундных пределах и возможном пересечении владельцев
после таймаута. Для `LiteScope` и полного `Scope` добавляются две формы
обновления — `setState` и `notifyDependents` — и особый жизненный цикл
состояния.

Имена внутри семейств достаточно последовательны, но одинаковое `of` возвращает
разные сущности: модель, контекст или состояние. Поэтому таблицы семейств
и типовые аксессоры действительно нужны. Ошибка в объяснении `Scope.of`
особенно неудачна именно на этом фоне.

Диагностика неправильного использования обычно полезна: она называет нарушенный
контракт и предлагает исправление. Два найденных дефекта показывают оставшуюся
проблему: понятное сообщение ещё не гарантирует безопасного отказа. После
отказа пакет должен оставить прежнего владельца и экран в предсказуемом
состоянии.

Человеческого прогона с измерением времени здесь не было. Утверждать, что
новичок освоит пакет за определённое число минут, оснований нет.

README с именами локальных файлов тем, dartdoc, quickstart и проверяемые
рецепты позволяют написать обычное приложение без чтения реализации.
Сохранённый Sol-прогон — реальное свидетельство этого для конкретной задачи:
приложение прошло приёмку, а затруднения записаны и разобраны.

Однако компилируемые блоки не защищают от ошибочной прозы вокруг них. Агент
может правильно следовать утверждению о синхронном контейнере и получить
некомпилируемый override; может обернуть `await close()` в `try/catch`
и ошибочно считать, что поймал все сбои автоматических зависимостей.

Нынешние эталоны переведены на `close()`, но историческое приложение
исполнителя и его приёмка относятся к прежнему решению. Это нормально для
истории; считать их независимой проверкой нового способа закрытия нельзя.

### Агент, который работает в репозитории

`AGENTS.md`, handoff, backlog и архитектурная карта дают хороший порядок
восстановления. Особенно полезны конкретные инварианты, объяснения SDK-кеша
и вердикты непосредственно возле старых находок. Они уменьшают риск повторно
«исправить» намеренное поведение.

Регламент объёмен, но большая часть правил имеет понятную причину. Исключение
для ревью без изменений удачно: агент не обязан загрязнять дерево отчётом
о чтении. Правила выпуска строгие, зато разрешение на публикацию не приходится
угадывать.

Слабое место — актуальность карты после нового механизма. В §8
`docs/architecture.md` подробно описан скриншотный путь, но общий барьер
закрытия асинхронных семейств отражён недостаточно. Второе трение — подготовка
свежего клона при незакоммиченной `.fvmrc`. Это устраняется небольшой правкой
входных инструкций, а не новым уровнем регламента.

## Нужен ли проект

**Да, для приложений, где часть дерева виджетов владеет ресурсами с длительным
созданием и освобождением.** База, плеер, соединение или сессия должны пережить
загрузку, корректно закрыться после детей и не пересечься с новым владельцем.
Здесь scopo объединяет несколько обычно раздельных механизмов.

Сравнение ниже основано на официальных материалах проектов, а не на собственных
сравнительных прогонах.

| Решение | Что уже закрывает | Когда scopo даёт дополнительную ценность |
|---|---|---|
| `provider` | Передача объектов по дереву, создание и освобождение, подписки и селекторы. [Документация](https://pub.dev/packages/provider). | Когда одного синхронного `dispose` недостаточно и нужны согласованные асинхронные этапы с UI. Для обычного `ChangeNotifier` преимущество scopo невелико. |
| `riverpod` | Асинхронное состояние, уничтожение состояния при прекращении использования, `onDispose`; генерация кода необязательна. [Жизненный цикл](https://riverpod.dev/docs/concepts2/auto_dispose), [генерация](https://riverpod.dev/docs/concepts/about_code_generation). | Когда нужна именно организация ожидаемого закрытия ресурса по дереву экранов, с отдельной closing-веткой и координацией следующих владельцев. |
| `flutter_bloc` | Организация бизнес-состояния и реакции UI; `BlocProvider` закрывает созданный им bloc. [Документация](https://pub.dev/packages/flutter_bloc). | Когда кроме состояния нужен общий протокол владения несколькими ресурсами. scopo может дополнять BLoC, не заменяя его модель событий. |
| `get_it` / `injectable` | Асинхронная готовность, скоупы, ожидаемый `popScope`, обратный порядок освобождения; `injectable` генерирует регистрацию. [Async objects](https://flutter-it.dev/documentation/get_it/async_objects), [Scopes](https://flutter-it.dev/documentation/get_it/scopes), [injectable](https://pub.dev/packages/injectable). | Когда удобнее объявить владельца прямо в дереве виджетов вместе с загрузкой, ошибкой и закрытием. Это ближайший конкурент по жизненному циклу, а не просто глобальный словарь сервисов. |

В частности, нельзя обосновывать scopo отсутствием асинхронного освобождения
у всех альтернатив: у `get_it` оно есть. Его документация также предлагает
привязку скоупа к жизни виджета через `watch_it`. Отличие scopo — в конкретной
объединённой модели, а не в уникальности каждого её элемента.
[Описание скоупов get_it](https://flutter-it.dev/documentation/get_it/scopes).

Пакет мало нужен приложению с простыми синхронными зависимостями или команде,
уже решившей эти задачи существующей инфраструктурой. Цена перехода — новые
семейства, правила подписок, отмены и освобождения. Для приложения
с действительно сложным временем жизни ресурсов эта цена может окупиться; для
счётчика или обычного CRUD-экрана — часто нет.

Главные препятствия принятию сейчас: небольшой внешний опыт, концентрация
сопровождения scopo и его асинхронного ядра у одного автора, а также
необходимость понимать исключения из общих обещаний. Добавление новых семейств
менее важно, чем устранение этих противоречий и проверка применения.

## Что в проекте сделано хорошо и что стоит сохранить

- **Проверяются трудные жизненные циклы.** Поздний ресурс, отмена, ошибка
  cleanup, повторное закрытие, отключённые кадры и порядок удаления потомков
  имеют отдельные сценарии. Число тестов здесь сопровождается содержанием.
- **Владение описано явно.** Различаются созданные и заимствованные модели,
  принятый и поздний результат инициализации, обычное удаление и закрытие
  на месте.
- **Таймауты не выдают за отмену работы.** README прямо предупреждает
  о возможном пересечении владельцев после истечения ожидания.
- **Документация исполняется.** Стенд примеров и проверки контрактов уже ловят
  большой класс регрессий; его нужно расширить на найденные границы,
  а не заменять.
- **Есть доступный первый пример и отдельное техническое демо.** Они решают
  разные задачи читателя.
- **История остаётся проверяемой.** Вердикты возле находок позволяют отличить
  исправление поведения от уточнения обещания.
- **CI проверяет объявленный нижний SDK и отдельно наблюдает новый stable.**
  Локальный прогон на нижней границе подтвердился.
- **Потребительский эксперимент хранит затруднения, а не только зелёный итог.**
  Это полезная практика, несмотря на дефекты вспомогательных инструментов.

  `return_of_invalid_type`. Находка 4 воспроизведена.
- `python3 probe_mutant_crash.py` на копии `tool/consumer_validation/`
  из клона — `Mutants: 10 KILLED, 0 SURVIVED, 0 INVALID`, `Classifier exit: 0`.
  Первый запуск упал на отсутствующем `kit/.review-tmp`: каталог в `.gitignore`
  комплекта, у ревьюера он был от прежних прогонов. После `mkdir` зонд прошёл
  как в отчёте. Находка 5 воспроизведена.
- `fvm dart doc --output` вне дерева — `Success!`; в `topics/Scope-topic.html`
  стоит `href="lite_scope.md#the-state"`, а в `topics/` есть только
  `LiteScope-topic.html`. Находка 7 воспроизведена.

Механизм каждой находки сверен с кодом:

- **1.** `ScopeAutoDependencies._runDispose` отдаёт сбой дерева
  в `FlutterError.reportError` и не бросает дальше; комментарий там же: «this
  method never re-throws». Абзац «Every step is guarded on its own…»
  в `doc/full_scope.md` обещает вызывающему `close()` первую ошибку и молчит,
  что ошибки автоматического контейнера до него не доходят. Подтверждаю.
- **2.** `LiteScopeElementBase.close` ставит
  `_screenshotCompleter ??= Completer<void>()` до `_performAsyncDispose`. Отказ
  `markNeedsBuild` во время сборки ловит обработчик
  в `AsyncScopeElementBase._runAsyncDispose`: он сбрасывает `_closingCompleter`
  и `_closeCompleter`, но не `_screenshotCompleter`. `buildOnReady` при
  непустом `_screenshotCompleter` строит `Stack` со снимком вместо состояния.
  Подтверждаю.
- **3.** В `AsyncControllerScopeElementBase.initDataAsync` строка
  `final controller = _controller = createController(this);` стоит раньше
  проверки `_controllerIsUnused(controller)`, а `onUnmount` зовёт
  `_controller?.performUnmount()`. Подтверждаю.
- **4.** Подтверждаю с оговоркой. Абзац «A container that needs no asynchronous
  work at all is returned as it is…» стоит под строкой «`initDependencies` is
  an ordinary `async` function», и в `async`-методе `return AppDependencies();`
  собирается. Но фраза «`AppDependencies()` satisfies [a `Future`] without a
  wrapper of any kind» сама по себе неверна, и зонд ревьюера прочитал её
  буквально. Два спутника по чтению тоже верны: абзац о первом параметре
  `ScopeAutoDependencies` говорит, что `Scope.of` отдаёт контейнер, хотя список
  аксессоров ниже в той же теме называет состояние; в `doc/debug.md`, «Coming
  from 0.9.x», стоит «The package has no external dependencies now»,
  а `pubspec.yaml` зависит от `async_job: ^0.3.0`.
- **5.** `run_acceptance.py` печатает `FAIL <имя> (no completion event)` для
  теста без `testDone`, а `run_mutants.py` считает каждую строку `FAIL ` (кроме
  `FAIL loading `) поведенческим провалом и при ненулевом коде даёт `KILLED`.
  Подтверждаю. Мои прогоны комплекта сегодня шли настоящим Flutter, и мутанты
  там падали на ассертах сценариев; находка — о том, что классификатор
  не отличил бы аварию.
- **6.** `verify.py` зовёт `git -C <kit> status` и сравнивает `vendor`
  с `KIT.parent/'scopo-src'`; `prepare.sh` не создаёт ни git в `kit/`,
  ни `scopo-src`. Подтверждаю с уточнением: живой порядок прогона
  в `docs/consumer-validation.md` `verify.py` не называет, его обещает только
  строка «Полный воспроизводимый прогон: python3 tools/verify.py …» в README
  комплекта — наследство проектировщика.
- **7.** Подтверждаю: из всех `doc/*.md` ссылка на `.md` одна, эта.

Конфликтов с регламентом ревьюер не назвал, кроме одного решения: полный
`prepare.sh` не запускал, потому что тот делает `git commit` в каталоге
прогона, а бриф запрещал коммиты. Решение верное, бриф это разрешал.

### `consumer-review/probe_mutant_crash.py`

```python
"""Exercise real classifier/acceptance code with an interrupted SDK event stream."""
import contextlib
import importlib.util
import io
import json
from pathlib import Path
import subprocess
import sys
from unittest.mock import patch

ROOT = Path(__file__).resolve().parent
KIT = ROOT / 'kit'

def load(name):
    spec = importlib.util.spec_from_file_location(name, KIT / 'tools' / f'{name}.py')
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    return module

acceptance = load('run_acceptance')
mutants = load('run_mutants')

def sdk_crash(command, **kwargs):
    if '--file-reporter' in command:
        path = Path(command[command.index('--file-reporter') + 1][5:])
        path.write_text(json.dumps({
            'type': 'testStart',
            'test': {'id': 1, 'name': 'a loading data and ordinary leave'},
        }) + '\n')
        return subprocess.CompletedProcess(command, 1, 'Test process exited unexpectedly.\n', '')
    return subprocess.CompletedProcess(command, 0, '', '')

stream = io.StringIO()
with patch.object(sys, 'argv', ['run_acceptance', str(KIT / 'reference/data')]), \
        patch.object(acceptance.subprocess, 'run', side_effect=sdk_crash), \
        contextlib.redirect_stdout(stream):
    acceptance_result = acceptance.main()
crash_output = stream.getvalue()
print('Actual acceptance output for one testStart and no testDone:')
print(crash_output)

calls = 0

def mutation_runner(command, **kwargs):
    global calls
    if command[0] == 'patch':
        return subprocess.CompletedProcess(command, 0, '', '')
    calls += 1
    if calls == 1:
        return subprocess.CompletedProcess(command, 0, 'All tests passed!\n', '')
    return subprocess.CompletedProcess(command, acceptance_result, crash_output, '')

with patch.object(mutants.subprocess, 'run', side_effect=mutation_runner):
    result = mutants.main()
print(f'Classifier exit: {result}; SDK was stubbed, no Flutter command ran.')
assert result == 0, 'Bug no longer reproduced'
```
